## Q1. What exactly does xAI's primary announcement say Grok Bot is and does, and what do third-party trackers add that xAI does not confirm?

### Takeaway
xAI's own announcement (Aug 11, 2026) defines Grok Bot as "your team of always-on agents" — named, persistent Bots that have "their own computer" in the cloud, "sign into the tools you already use", work "inside tools and apps like you do", "keep working 24/7", and "only come back when something needs your approval". Later xAI design and enterprise posts add the vocabulary of persistent agents, Routines (scheduled/event-triggered work) and "standing responsibility"; the phrase "standing agent" as a product label appears in third-party trackers, not in xAI's launch post.

## Q4. What is the architecture: where the agent runs, which model powers it, how it authenticates into the user's accounts, and where credentials are stored?

### Takeaway
Each user gets one persistent Firecracker microVM in Cursor's US cloud (not xAI's and not the user's); all of a user's Bots share that computer, its browser sessions, files and CLI credentials. Model selection is managed by Cursor/Grok Bot with no picker: xAI first-party models plus third-party models on Cursor's sub-processor list, with Claude Opus 5.5 explicitly named (Musk, Oct 7; Cursor help page). Sign-in is "as the member": the Bot has no identity of its own, the user types passwords/2FA/CAPTCHA via a "takeover" of the cloud computer, OAuth connector tokens stay on Cursor's backend, and a write-only "secure secret" store holds API keys. On-premises or self-hosted deployment is explicitly not supported.

### Cited Findings
- Runtime location: "It runs in Cursor's cloud, and each user's work executes on a dedicated cloud computer." "Per-user isolation. Each user's work runs in a dedicated Firecracker microVM, a micro virtual machine with hardware-level separation from other users." — [docs.x.ai/grok-bot/teams-and-enterprises](https://docs.x.ai/grok-bot/teams-and-enterprises.md)
- Shared-computer model: "All of your Bots use the same cloud computer, sharing its files, browser sessions, and app logins... The computer belongs to your account, not to an individual Bot, so treat anything placed on it as available to every Bot you run; between users, isolation is strict." — [docs.x.ai/grok-bot/overview](https://docs.x.ai/grok-bot/overview.md); "Browser cookies and signed-in sessions are shared; Files are visible to every Bot; Command-line credentials are shared". — [docs.x.ai/grok-bot/computer-and-apps](https://docs.x.ai/grok-bot/computer-and-apps.md); "Isolation is per user, not per Grok Bot." — [x.ai/bot](https://x.ai/bot)
- Request path: "The Grok Bot desktop and mobile apps send each request to Cursor's servers. - Hosting constraints: "Grok Bot runs only on Cursor-hosted cloud computers. On-premises deployment, deployment inside your own perimeter, and bring-your-own-image deployment are not supported today." and "Grok Bot computers run in the United States today." — [docs.x.ai/grok-bot/security](https://docs.x.ai/grok-bot/security.md)

## Q5. Where does Grok Bot's knowledge of the user live, how does it ingest user knowledge, and can the user view, edit, export or delete it? How does this relate to Grok's consumer memory?

### Takeaway
Grok Bot's "knowledge" is (a) per-Bot memory described only as "stable preferences, role context, and summaries of prior work", (b) files on the shared cloud computer's /workspace, (c) persistent browser sessions and plugins/connectors, and (d) Skills/Routines. There is no document store, no typed schema, no revision history and no user-facing memory browser or export documented; xAI's own docs say memory "is not a substitute for an authoritative source". Deleting a Bot does not delete files, sessions or routines. Consumer Grok (grok.com) has a separate "Memory across chats" feature with Data Controls (Improve the Model, Personalize Grok using X, Private Chat, Delete All Conversations, download data) under xAI's consumer policy; Grok Bot does not use those controls.

## Q7. Can Grok Bot (or the Grok app) be pointed at a user's own MCP server or REST API? Is there an xAI MCP server and a connectors catalogue?

### Takeaway
Yes, in two ways. Grok Bot supports custom MCP servers as plugins ("Remote HTTPS" with its own credential or OAuth, or "Command" servers run on the cloud computer), inherits Cursor's MCP/connector policy, and can also hit any REST API from its shell or browser. Consumer Grok (grok.com) supports "Bring your own MCP" custom connectors but requires the server to be on the public internet and rejects localhost/private addresses (xAI's docs recommend ngrok or Cloudflare Tunnel). xAI publishes an MCP server for its own docs, "Remote MCP tools" in the API, and a connector catalog at grok.com/connectors. Reaching a private-network server from Grok Bot requires routing egress through the user's desktop (per-desktop toggle) or an Enterprise-only Team Setup networking client (Tailscale/Cloudflare examples).

### Cited Findings
- Grok Bot plugin types include custom MCP: "Custom MCP server, Remote HTTPS — The Bot's own credential, or each person's sign-in if the server uses OAuth — None, or a one-time sign-in"; "Custom MCP server, Command — Runs on the computer each conversation uses"; "For a custom server that needs secrets, choose Remote HTTPS." — [docs.x.ai/grok-bot/team-bots](https://docs.x.ai/grok-bot/team-bots.md)

## Q8. What is the approval and audit model for actions and writes? What needs approval, what can run unattended, and what read-only modes exist?

### Takeaway
Approvals are prompt-driven and model-mediated: the user writes boundaries in prose, an "Auto Review" model decides whether an action proceeds, needs approval or is denied, and approval cards offer Allow once / Always allow (saves a standing rule) / Deny. Unattended work (routines, triggers, Bot-to-Bot) is explicitly supported; its approval cards expire after about 10 minutes and the action simply does not run. Auto Review does not cover memory writes; approvals never reverse completed work; the terms say approval controls are "aids only" and disclaim liability. There is no read-only mode; "read-only" is achieved by scoped credentials or prose. Per-action audit (Action Recording), audit logs and OpenTelemetry export are Enterprise-only and off by default; individuals get a transcript and usage views.

### Cited Findings
- What requires approval: "The answer depends on the tool, the risk of the action, and—when enforcement is enabled—your Auto-review rules. Sensitive or consequential actions can stop for approval. Passwords, two-factor codes, CAPTCHAs, and similar human-only steps use a computer takeover. Put standing boundaries in each Bot's description and add narrow Ask first rules for actions such as sending, publishing, deleting, purchasing, or changing production systems." — [docs.x.ai/grok-bot/faq](https://docs.x.ai/grok-bot/faq.md)
- Approval card: "When an action needs approval, the conversation shows the proposed operation and its inputs. Allow once lets the Bot continue with that action, Always allow can save a matching rule, and Deny blocks it... An approval controls the proposed action, not work already completed, and nobody should approve an action whose target or effect they cannot identify." — [docs.x.ai/grok-bot/security](https://docs.x.ai/grok-bot/security.md)
- Auto Review scope: "an independent review model that evaluates risky Bot actions before they run, covering shell commands, plugin calls, computer use, automation writes (changes to routines and event triggers), and delegation such as Cloud Agent and subagent launches. It can let an action proceed, require approval, or deny it." "It does not review every side effect. Memory writes and most settings changes are examples. Treat it as a complement to explicit boundaries and least privilege". — [docs.x.ai/grok-bot/security](https://docs.x.ai/grok-bot/security.md)
- Rules: "Ask first rules always stop matching actions. Allow automatically rules let matching actions proceed only when the reviewer finds no other reason to stop... Ask first wins when rules conflict." Personal rules "are stored on the current desktop and synced to its Grok Bot computer, so another desktop installation needs its own." — [docs.x.ai/grok-bot/approvals-security-and-privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy.md)
- Unattended approvals: "An approval from work that started without you, such as a routine, a trigger, or a message from another Bot, expires after about 10 minutes; the card then shows Expired, and the action does not run. An expired card may offer Always allow this in the future, which adds the proposed rule to your Allow automatically rules without running the expired action." — [docs.x.ai/grok-bot/approvals-security-and-privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy.md)
- Recommended boundaries: "Prefer explicit boundaries for: Sending messages or invitations; Publishing content; Purchases and financial transfers; Deleting or overwriting data; Changing permissions; Production changes; Accepting legal terms." Least privilege: "Start with read-only tasks and draft outputs. Keep sending, publishing, purchasing, deletion, and production changes behind approval." — [docs.x.ai/grok-bot/approvals-security-and-privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy.md)
- Boundaries live in prose: "Use the description for rules that should remain true: Description: 'Never send external messages without approval.'" — [docs.x.ai/grok-bot/bots](https://docs.x.ai/grok-bot/bots.md). Enterprise "Team Rules" are also prose ("never move company data to personal accounts"): "Rules guide a Bot; for approval behavior, use Auto-review rules." — [cursor.com/docs/grok-bot/teams](https://cursor.com/docs/grok-bot/teams.md)
- Enforcement is Enterprise-only: "Team admins can enforce Auto-review. Enterprise only." "Enforce Auto-review... is off by default." — [docs.x.ai/grok-bot/security](https://docs.x.ai/grok-bot/security.md); [docs.x.ai/grok-bot/teams-and-enterprises](https://docs.x.ai/grok-bot/teams-and-enterprises.md)
- Drafts for email/Slack: "When a Bot prepares an email or Slack message, the conversation can show a New Email or New Slack Message card. Choose Send Email or Send Message, or Discard." — [docs.x.ai/grok-bot/mobile](https://docs.x.ai/grok-bot/mobile.md); Agent Email: "Bots send only when the member has asked them to and otherwise show the draft first". — [cursor.com/docs/grok-bot/teams](https://cursor.com/docs/grok-bot/teams.md)

- Test runs are live: "a test run performs real work". — [eesel.ai review (secondary)](https://www.eesel.ai/blog/grok-bot-review)
- Marketing shows unattended autonomy as the goal: "Put a few Bots in the same thread and they pass work between themselves. (employee quote) — [x.ai/news/introducing-grok-bot](https://x.ai/news/introducing-grok-bot)

### Inferences
- The approval model is permission-by-prose plus a model-judged reviewer; nothing structural prevents a write (an "Always allow" rule or a Bot description can let sends, purchases or deletions run unattended), and memory writes are never gated. This is the inverse of a system where every write is a proposal requiring interactive human approval.
- Per-action audit for individuals is effectively the chat transcript; a credential-attributed write log exists only as Enterprise Action Recording with 90-day retention.

### Gaps

### Inferences
- Replace: no. Grok Bot has no vault, no typed properties/people/time model, no revision-cited retrieval, no explicit "nothing found vs retrieval degraded" distinction, and no owned/exportable knowledge; its own docs tell users to keep facts "in the source system".
- Compete: yes, for mindshare and spend as the "always-on personal agent", and for the automation use cases (inbox, routines, briefings) a SecondBrain chat assistant plus MCP clients might otherwise cover; its marketing of unattended autonomy is the opposite of SecondBrain's proposal-and-approve posture.
- Complement: only in a non-`local_only` configuration. A plausible pattern is SecondBrain as a "Remote HTTPS" MCP plugin reached via Cloudflare Tunnel + Access (the Bot's browser can complete the Access login, and OAuth-protected custom MCP servers are supported) or via egress routed through the user's desktop on the tailnet. Either way SecondBrain excerpts would transit a US cloud VM and an undisclosed mix of xAI and third-party models, and SecondBrain's write proposals would be approved by a Grok Bot "Always allow" rule or expire unattended — defeating the interactive-human-approval invariant. With `local_only` enforced at the transport and a firewall canary, Grok Bot cannot reach SecondBrain at all, which is the intended outcome.
- What it cannot give the target user: (1) local-only operation — hosted-only, US-only, no on-prem; (2) model control — no picker, no local vLLM, undisclosed third-party routing; (3) owned, typed, cited knowledge — opaque per-Bot memory, no export, memory writes unreviewed; (4) structural write safety — prose boundaries and a model reviewer rather than a proposal queue; (5) per-turn exposure accounting — no egress manifest, allow-all egress by default; (6) credential-attributed audit — Enterprise-only Action Recording with 90-day retention; (7) separation of concerns — one shared browser/credential profile for all Bots.
- The cleanest way for Grok's ecosystem to touch SecondBrain without violating its invariants is not Grok Bot but a local MCP-capable client (Claude Code/Desktop, or OpenClaw/Hermes using a Grok subscription) running on the user's own machine inside the tailnet.

### Gaps
- No user report of connecting Grok Bot to a self-hosted MCP server behind Tailscale/Cloudflare Access was found; the reachability analysis is derived from the docs, not tested.
- Whether Grok Bot's custom-MCP OAuth flow supports Cloudflare Access (OIDC) specifically is undocumented.
