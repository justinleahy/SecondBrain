## KQ1. What does OpenAI's own announcement say, and which widely repeated claims come only from secondary coverage?

### Takeaway
OpenAI's own pages (announcement, safety post, FAQ, system-card appendix, DevDay recap) establish: launched 2026-09-29 at DevDay 2026 in San Francisco; "remarkably capable, always-on agents built to handle everything"; powered by GPT-6 Astra (name confirmed by OpenAI, not just press); each dot has its own cloud Linux computer and Chrome browser; "learn from feedback over time"; "work towards your goals 24/7"; connect to "over 4,000 apps" through OpenAI's own plugin ecosystem (not a Zapier figure); available on Pro and Business Premium in eligible markets, with an admin-enabled, off-by-default beta for Enterprise/Edu/Healthcare; one "primary dot" per user for now. Claims that come only from secondary coverage include the "GPT-6.1 Astra" model name (wrong — that model was cancelled), "hardware-enforced isolation / automatic quarantine", an OSWorld 2.0 score, and the idea that Dots "lied to users in testing" (that WSJ reporting was about the cancelled GPT-6.1 Astra model, not Dots).

## KQ2. Where does a dot's knowledge of the user live, can the user export it, and is it used for training?

### Takeaway
A dot's knowledge is an opaque "context" held by OpenAI for as long as the dot exists, two-way-linked to ChatGPT Memory, and fed by connected plugins (Gmail, Drive, Slack, calendar, etc.) and by background "proactive research" notes. Users cannot view, edit or delete individual dot memories; the only control is deleting/resetting the whole dot or disconnecting apps (which does not remove what was already learned). No export of dot context is documented; the only route is a jurisdiction-dependent data-subject request. On personal plans, dot conversations and actions are used for training unless "Improve the model for everyone" is off; Business/Enterprise/Edu are excluded by default; human review can occur even when training is off. Dots do not support data residency and OpenAI says they do not provide "strict zero data retention". Nothing OpenAI publishes describes retrieval with citations in dot work products.

### Cited Findings

**What is remembered and where**
- "Your dot can retain context from your conversations and plugins for as long as you keep your dot. You can delete your dot's context by deleting your dot. Any information that your dot has shared with ChatGPT Memory can be separately managed in ChatGPT Memory settings." — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary, Wayback 2026-10-03]
- "Your dot's context does not retain credentials, images, or screenshots. Files your dot creates or uses in other locations, such as ChatGPT Library, your computer, or a connected storage service, follow that location's retention policies." — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary]
- "Dots build context over time to make their help more useful. When they delegate work, the other agents are instructed to keep the information needed for the task and avoid retaining unnecessary sensitive details. Each dot has its own context that you can reset at any time." — [OpenAI safety post](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/) [primary]
- Relation to ChatGPT Memory: "Your dot can receive memories and recent conversation context from ChatGPT, and conversations with your dot can contribute to memory in ChatGPT. Memory can continue to be shared between ChatGPT and your dot after setup. Turning off Memory in ChatGPT stops that sharing. It does not delete information that your dot has already received." — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary]
- But not everything in ChatGPT is pre-loaded: "dots don't have access by default to everything you have shared with ChatGPT already." — Thibault Sottiaux, [Willison live blog, 16:34](https://simonwillison.net/2026/Sep/29/openai-devday-2026-live-blog/) [primary press]
- Proactive-research notes: background tasks "use read-only tools to gather information from permitted connected sources, then save private notes for that dot." — [OpenAI safety post](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/) [primary]
- Storage location is OpenAI's cloud; AIMultiple summarises "Dots keeps memory on OpenAI's side, and clearing it means deleting the dot" — [AIMultiple, 2026-09-30](https://aimultiple.com/always-on-agents) [secondary, consistent with the FAQ]

**Inspect / edit / export / delete**

### Inferences
- A dot's "memory" is not a knowledge base a user owns: it has no schema, no inspection, no export, and its boundary with ChatGPT Memory is one-way leaky (switching Memory off stops future sharing but not what was already copied).
- The training default on personal plans is opt-out, and the FAQ's "data from connected apps" clause means Gmail/Drive content a dot reads can become training data unless the user has opted out — a materially broader surface than chat text.
- The "Improve the model for everyone" opt-out does not stop human review, and the EEA/UK/CH exclusion plus the "no residency during beta" statement implies that an EU-based privacy-conscious user is outside the product by design for now.

### Gaps
- Whether ChatGPT's general "export data" function includes dot context is not stated anywhere I could reach.
- Retention period for dot context after deletion (backup windows) is not specified on the dots pages.
- No OpenAI document describes citation or provenance in dot outputs.

## KQ3. What are the concrete approval, read-only and audit mechanisms, and what can a dot do while the user is away?

### Takeaway
There are five documented layers: model training (Astra), plugin permissions, user-set Custom Rules (allow / pre-approve / ask first / block), a separate "Auto-review" model that checks consequential actions and cannot be switched off by the dot, and safety monitoring that can pause a dot. While the user is away a dot may continue previously authorised tasks and run "proactive research", which is enforced in code as read-only (no sending messages, no changing app content, no browser/computer control). Mandatory hand-offs: password changes and money transfers always return to the user; permanent deletion, installing software from unrecognised sources and granting new security-sensitive access need per-instance confirmation; purchases on saved merchant cards need approval. Audit for individuals is "Activity View" in the desktop app; for Enterprise, a Compliance API with explicitly incomplete coverage. There is no documented spending cap.

### Cited Findings

**Built-in rules, Custom Rules, hand-offs**
- "Dots start with built-in rules for when to act independently and when to ask for approval. Custom Rules let you allow specific actions, require approval, or block them. Built-in safety requirements always apply and you can follow progress, including background work, in Activity View and redirect dots as needed." — [Introducing dots](https://openai.com/index/introducing-dots/) [primary]
- FAQ policy list: "The most sensitive actions like changing a password or transferring money require you to take over so you can complete them yourself"; "Other actions like permanently deleting data or installing software may require approval each time"; "In some of these cases such as sending recurring messages, you can give your approval in advance instead of each time" — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary]
- Scope of an approval: "Approving one message does not give your dot ongoing permission to contact people on your behalf. Any advance approval remains limited to what you authorized." — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary]

### Inferences
- The approval model is action-class based but tuned conservatively, producing "approval fatigue" in practice (eesel scores day-to-day friction 2.5/5; HN commenters warn per-call approval "trains you to say yes"). SecondBrain's proposal model is coarser (every write is a proposal) but is enforced server-side rather than by a second LLM.
- "Read-only while away" is narrower than it sounds: it governs only the self-initiated research mode; any task the user authorised earlier keeps running with write capability subject to Auto-review.
- The audit story is weakest exactly where SecondBrain is strongest: there is no per-write credential attribution visible to the user, and Enterprise docs concede the trail does not cover every subagent path.

### Gaps
- No OpenAI page documents a user-facing exportable log of actions taken (Activity View is in-app only).
- No published figures for how often Auto-review blocks real actions in production.
- The 2026-10-02 hands-on review summarised by NeoTeo could not be traced to its original outlet.

## KQ4. Can a dot be connected to a self-hosted MCP server, over which transport and with what auth?

### Takeaway
By OpenAI's own documentation chain the answer is "very probably yes, remote-only": custom MCP servers are added in ChatGPT as plugins ("Add custom MCP server" → "Create as a plugin"), plugin permissions are explicitly shared with dots, and OpenAI's MCP Events doc explicitly says events work "with dots". Supported transports are Streamable HTTP and HTTP/SSE over public HTTPS; stdio is only reachable through OpenAI's outbound-only "Secure MCP Tunnel", which the tunnel page documents for ChatGPT, Codex and the Responses API but does not mention for dots. Auth options are OAuth (static credentials, CIMD, or DCR), no auth, or mixed. Model choice is OpenAI-only. I found no published confirmation from OpenAI or a tester that a dot has actually invoked a custom MCP plugin; one developer's spike to verify it was still open on 2026-10-02.

### Cited Findings

**Plugins are the integration surface for dots, and plugins can be MCP servers**
- "Through our ecosystem of plugins, they can readily connect to over 4,000 apps" — [Introducing dots](https://openai.com/index/introducing-dots/) [primary]
- "Plugin permissions are shared across dots, ChatGPT, ChatGPT Work, and Codex. Your dot can use your existing connections within the permissions you've granted." and "You can connect new plugins and manage existing ones in ChatGPT's Plugins tab. These connections are shared across dots, ChatGPT, ChatGPT Work, and Codex." — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs) [primary]
- A plugin "can contain skills, an MCP server, both, or lifecycle hooks"; "Build an MCP server when the plugin must connect to a service, expose controlled tools, authenticate users, or run on infrastructure you operate"; UI uses "the open MCP Apps UI standard" — [Plugin architecture](https://developers.openai.com/plugins/concepts/plugins) [primary]
- MCP Events (the proposed spec OpenAI adopted at DevDay) "works in Work chats on ChatGPT web, in Work chats in the desktop app with Cloud selected, and with dots." Requires MCP protocol version 2026-07-28 with `server/discover`; webhook-only delivery; "Callbacks must use HTTPS … private, local, and other non-public addresses are blocked. Redirects are not followed." — [MCP Events](https://developers.openai.com/plugins/build/mcp-events) [primary]; announced as "MCP events for plugin automations" — [DevDay 2026 Recap](https://openai.com/index/devday-2026-recap/) [primary]
- Workspace side: "Plugin controls determine which apps are available and which actions they can perform. App permissions determine when an app action requires approval." — [Manage dots](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces) [primary]

**How a custom (self-hosted) MCP server is added, transports, auth**
- "Go to ChatGPT Plugins, select the plus button, then choose 'Add custom MCP server.' … Enter a name, optional description, and a Server URL (or select Tunnel for a Secure MCP Tunnel). Configure authentication, review the risk warning, select 'I understand and want to continue,' then select 'Create as a plugin.'" Transports listed: SSE and streaming HTTP (no stdio). Auth: "OAuth, No authentication, or OAuth or no authentication"; OAuth "uses static credentials if provided. Otherwise, it can use Client ID Metadata Documents (CIMD) when the authorization server supports them, or Dynamic Client Registration (DCR) when configured." Mixed mode: no auth for initialize/list-tools, per-tool OAuth from tool metadata. — [Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server) [primary]
- Write safety in ChatGPT for custom servers: "Write actions require confirmation by default. ChatGPT respects the `readOnlyHint` annotation, and tools without it are treated as write actions." Approve/deny can be remembered for a conversation only. Warning: "Only connect to MCP servers you trust." — [Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server) [primary]
- Developer mode location and tunnelling for local testing: "Settings → Security and login", turn on Developer mode; expose a local server with ngrok and supply the public URL with the `/mcp` path; use OAuth 2.1 when user auth is required; "OpenAI-managed mTLS to authenticate ChatGPT as the MCP client" — [MCP server and UI quickstart](https://developers.openai.com/plugins/build/app-quickstart) and [Build an MCP server](https://developers.openai.com/plugins/build/mcp-server) [search extractions]
- "Account and workspace policies apply to adding and using custom MCP servers." Tunnels "do not replace the public HTTPS endpoint required for" plugin submission. — [Connect and test your plugin](https://developers.openai.com/plugins/deploy/connect-chatgpt) [primary]

- "An MCP tunnel is an outbound-only connection from a host inside your network to an OpenAI-hosted MCP endpoint." **Model choice**
- Only OpenAI models: "Powered by GPT‑6 Astra" — [Introducing dots](https://openai.com/index/introducing-dots/); "Enterprise model controls and default model settings do not apply to dots." — [Manage dots](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces) [primary]. ### Inferences
- For SecondBrain specifically: a dot could in principle call SecondBrain's MCP server if SecondBrain is exposed as a remote Streamable-HTTP endpoint over public HTTPS (e.g. the Cloudflare Tunnel path) with OAuth, registered as a custom plugin by the same ChatGPT account. A Tailscale/WireGuard-only endpoint cannot be reached (OpenAI's cloud computer "does not automatically inherit a member's local VPN"), and MCP Events webhooks explicitly reject non-public addresses. Cloudflare Access in front of the endpoint would have to be replaced or bypassed by the MCP server's own OAuth, because ChatGPT performs OAuth discovery against the server, not a Cloudflare login page.
- The Secure MCP Tunnel is the only documented route for a stdio or private server, but it requires an OpenAI Platform organisation, a runtime API key, and a long-running outbound client, and its support for dots is undocumented.
- Write protection would be double: ChatGPT/Auto-review on the dot side, and SecondBrain's own proposal queue on the server side (a dot can only create proposals; approval still needs a human in SecondBrain's interactive session). Read exposure, however, is entirely governed by SecondBrain's per-turn egress controls, since OpenAI's side would ingest whatever the tools return into an opaque, exportless dot context.

### Gaps
- No OpenAI page states in one place "dots can use custom MCP plugins"; the conclusion rests on (plugins shared with dots) + (custom MCP servers become plugins) + (MCP Events "with dots").
- Whether a Secure MCP Tunnel-backed plugin is reachable from a dot is not documented.
- Whether personal (Pro) accounts can use `readOnlyHint`-style per-tool approval memory inside a dot (as opposed to a ChatGPT chat) is not documented.

## Versus SecondBrain: replace, compete, or complement?

### Takeaway
Dots does not replace a self-hosted, typed, cited knowledge daemon; it is a hosted "doer" whose knowledge is an opaque, non-exportable, training-eligible context in OpenAI's cloud, running an OpenAI-only model, outside the EEA/UK/CH for individuals, with no local-only mode and no per-write credential attribution. It competes only at the level of the convenience pitch ("an assistant that knows my stuff and acts"), and only for users who accept cloud custody. It could complement SecondBrain as an MCP client — but only if SecondBrain is exposed over public HTTPS with OAuth, which is precisely what `local_only` forbids; and even then the dot would copy whatever it reads into its own unauditable memory.

### Cited Findings (mapping SecondBrain's commitments to what dots documents)
- Owned, typed knowledge in a Markdown vault + SQLite: dots has no user-visible store; "You currently cannot view, delete or directly modify individual dot memories" — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs); no export beyond DSAR — same page.
- Who/when/which-type as SQL: not applicable; dots' memory is unstructured context; "It is not clear whether memories are injected at every turn and what is injected." — [HN](https://news.ycombinator.com/item?id=49896604)
- Citations and "nothing found" vs "retrieval degraded": no OpenAI dots page documents citations; the only degraded-state signal reported is incidental (a Gmail read cap "and it said so plainly") — [XDA](https://www.xda-developers.com/openais-dots-gave-me-what-wanted-from-openclaw-without-the-hassle/)
- Every write is a human-approved proposal: dots' nearest equivalents are Custom Rules + Auto-review + mandatory hand-offs, enforced by OpenAI-side models and policy, with advance approvals allowed — [OpenAI safety post](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/); and the user can broaden sharing rules, e.g. "share with any online form" — same page.
- Per-turn egress cap and manifest: nothing comparable; Custom Rules "govern what a dot may do, not which fields reach its model" — [NeuralTrust](https://neuraltrust.ai/blog/chatgpt-agent-security); connected-app data can become training data on personal plans — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs)
- Credential recorded per write: no user-facing equivalent; Enterprise audit "does not … cover every internal subagent path" — [learn.chatgpt.com](https://learn.chatgpt.com/docs/enterprise/cloud-local-access)
- Model choice / local vLLM reference: dots are "Powered by GPT‑6 Astra" only; admin model controls "do not apply to dots" — [Introducing dots](https://openai.com/index/introducing-dots/); [Manage dots](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces)
- `local_only` enforced at transport + firewall canary: dots require OpenAI's cloud computer; the only private-server bridge is an outbound tunnel to `api.openai.com:443` — [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels); MCP Events reject private addresses — [MCP Events](https://developers.openai.com/plugins/build/mcp-events)
- WireGuard/Tailscale or Cloudflare Tunnel + Access reachability: "A dot's cloud computer does not automatically inherit a member's local VPN, browser sign-ins, or device policies." — [Manage dots](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces)
- MCP server for Claude Code/Claude Desktop: dots is an MCP *client* surface via plugins; "Plugin permissions are shared across dots, ChatGPT, ChatGPT Work, and Codex" — [Dots FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs); custom MCP servers are added via "Add custom MCP server … Create as a plugin" with OAuth/none — [Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)
- Availability to a European user: Pro excluded in EEA/CH/UK — [TNW](https://thenextweb.com/news/openai-dots-always-on-ai-agents-cloud-computers-devday); Business Premium (US$100–125/seat, 2-seat minimum) is the workaround — [help.openai.com billing](https://help.openai.com/en/articles/8792536-managing-billing-and-seats-in-chatgpt-business) [search extraction]
- Price floor for an individual: US$100/month (Pro 100) — [help.openai.com Pro tiers](https://help.openai.com/en/articles/9793128-about-chatgpt-pro-tiers) [search extraction]; SecondBrain's reference is a self-hosted vLLM box (no per-seat fee).

### Inferences
- **Replace?** No. Dots lacks every property SecondBrain defines itself by (ownership, typing, citations, egress manifest, credential attribution, local-only, model choice). It also lacks the thing a knowledge daemon exists for — a durable, inspectable store — since the only way to "edit" a dot's knowledge is to delete the dot.
- **Compete?** Partially, on the "assistant that remembers me and acts" narrative for users who already live in ChatGPT; price (US$100+/month), desktop-only creation, EU exclusion and opt-out training defaults narrow that overlap for a privacy-conscious technical user. The sharper competitive pressure is on the *acting* side (dots executes; SecondBrain only proposes), which SecondBrain does not try to match.
- **Complement?** Technically plausible once SecondBrain's MCP server exists: register it as a custom plugin (public HTTPS, Streamable HTTP, OAuth via CIMD/DCR), after which the dot could query typed facts with citations and submit proposals. Two caveats make it a poor fit: (1) it requires turning `local_only` off and exposing the daemon on the public internet with its own OAuth rather than behind Cloudflare Access; (2) everything the dot reads is copied into an OpenAI-side context that cannot be inspected, exported or selectively deleted and (on Pro) is training-eligible unless opted out — so SecondBrain's egress manifest would be the only record of what left the vault.
- **What dots cannot give the SecondBrain user:** owned data, a schema, SQL-answerable who/when/which, cited revisions, explicit degraded-state reporting, a per-turn exposure cap, write attribution, model choice, enforced local-only operation, EU availability on a personal plan, under-18 use, or any audit trail that OpenAI itself describes as complete.

### Gaps
- No tester has publicly demonstrated a dot invoking a custom MCP plugin, so "complement" is an inference from OpenAI's docs, not an observed capability.
- SecondBrain's MCP server and chat are not yet implemented (foundations milestone only as of 2026-10-09), so any integration test is hypothetical.
