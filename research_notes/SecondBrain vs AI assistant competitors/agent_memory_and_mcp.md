# AI agent memory layers and MCP memory/knowledge servers versus SecondBrain (state as of 2026-10-09)

Scope: Mem0 (incl. OpenMemory MCP), Supermemory, Letta, Zep/Graphiti, Cognee, Basic Memory in depth; vendor-native memory (Anthropic, OpenAI, Google), the reference MCP memory server, LangMem, Honcho, Memori and other 2025-2026 entrants briefly; and the state of the Model Context Protocol itself. Every figure is dated; anything older than 2025 is flagged as possibly stale. "SecondBrain" facts come from the repo's `spec.md` and the assignment brief, not from web sources.

## KQ1: What is each system, who makes it, and how does it score on the comparison fields? (self-contained per-system profiles)

### Takeaway
The six in-depth systems split into three shapes: LLM-extracted "memory items" in a vendor or vector database (Mem0, Supermemory), LLM-extracted temporal knowledge graphs (Zep/Graphiti, Cognee), and plain Markdown files edited by the agent (Letta's git-backed MemFS, Basic Memory). Only the Markdown-file systems give the user an owned, readable, versioned artefact; none of the six requires a human to approve an agent's write, delete or overwrite (Supermemory's review queue covers only inferred memories and Zep Cloud offers only read-only MCP connections); and all six except Letta/Basic Memory depend on an LLM extraction step whose failures (Mem0 issue #4573's 97.8% junk audit, Graphiti issue #1728's 16-41% wrongful fact invalidation) are the dominant 2026 complaint.

Architecture and storage
- Two products: OSS library/Docker "with your data on your infrastructure" and the hosted Platform keyed by API key — [docs.mem0.ai llms.txt](https://docs.mem0.ai/llms.txt)
- OSS storage = a vector store (15 supported) plus a SQLite `history` table whose `SQLiteManager` defaults to `db_path=":memory:"` (history lost at process exit unless a path is given); columns id, memory_id, old_memory, new_memory, event, created_at, updated_at, is_deleted, actor_id, role — [storage.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py)
- OSS graph memory was removed: the OSS graph page states a release deleted all external graph-store drivers (Neo4j, Memgraph, Kuzu, Apache AGE, Neptune; "~4000 lines") and the `relations` search field with "no OSS replacement"; graph memory is now a Platform feature "built in and always on" (no version/date on the page; conflicts with earlier cached snippets listing those backends) — [OSS graph memory page](https://docs.mem0.ai/open-source/graph_memory/overview)
- Memory is never a user-owned plain file: OSS = vector-DB rows + SQLite history; Platform = Mem0 cloud with a Memory Export feature — [Memory Export](https://docs.mem0.ai/platform/features/memory-export)
- Data model: memory items scoped by `user_id` / `agent_id` / `app_id` / `run_id`, free-form metadata, categories; Platform adds per-operation events — [Entity-scoped memory](https://docs.mem0.ai/platform/features/entity-scoped-memory); [Mem0 MCP](https://docs.mem0.ai/platform/mem0-mcp)
- Hosted-only: graph memory (Pro+), "Dream" memory consolidation (Pro+), advanced analytics, hosted MCP, the Claude Code plugin backend, audit logs / SSO / on-prem (Enterprise) — [Pricing](https://mem0.ai/pricing); [Dream](https://docs.mem0.ai/platform/features/dream)

How memories are written
- Paper method (Apr 2025): extraction phase (LLM extracts candidate facts from the latest message pair plus a rolling summary and last 10 messages) then update phase (retrieve top-10 similar memories; LLM tool call chooses ADD / UPDATE / DELETE / NOOP) — [arXiv HTML](https://arxiv.org/html/2504.19413v1)
- OSS today (read 2026-10-09): "Single-pass ADD-only (one LLM call, no UPDATE/DELETE)"; `add()` returns only ADD events; changed facts are stored beside old ones and ranking is expected to surface the current one; exact duplicates blocked by MD5 hash; `custom_fact_extraction_prompt` renamed `custom_instructions` — [OSS graph memory page](https://docs.mem0.ai/open-source/graph_memory/overview)
- Platform still exposes agent-driven `update_memory` (overwrite text/metadata) and deletes — [Mem0 MCP](https://docs.mem0.ai/platform/mem0-mcp)
- Claude Code plugin (`claude plugin install mem0@mem0-plugins`, requires a Platform key): hooks capture user messages, Claude answers, changed files and test/build output locally and flush batches to Mem0 after every 5 exchanges, on session end/compaction, or after 5 min idle; extraction runs in Mem0's hosted background worker; `/mem0:remember` for explicit saves; the earlier MCP server was replaced by a single read-only `search_memories` tool — [Claude Code integration](https://docs.mem0.ai/integrations/claude-code)

How memories are retrieved
- OSS hybrid search: semantic + BM25 keyword boost (needs qdrant-client >= 1.12 + `fastembed`) + spaCy entity matching (`[nlp]` extra); BM25/entity signals only re-rank, never add candidates; defaults top_k 20, threshold 0.1, rerank False; "graceful degradation": missing spaCy/fastembed silently disables those features — [OSS graph memory page](https://docs.mem0.ai/open-source/graph_memory/overview)
- Platform: `rerank` (adds ~150-200 ms), V2 filters, top_k, threshold — [Advanced retrieval](https://docs.mem0.ai/platform/features/advanced-retrieval); [V2 filters](https://docs.mem0.ai/platform/features/v2-memory-filters)
- No SQL-style who/when queries; a maintainer closing issue #4573 cited Platform "temporal reasoning" (June 2026) and "memory decay" (May 2026) — [issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- Whether search responses include a score/uncertainty field was not confirmed (gap)

Provenance, revisions, citations
- OSS history rows carry `actor_id` and `role` plus old/new text and event — [storage.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py)
- Platform: Memory History API; MCP `list_events` / `get_event_status` expose operation events — [History API](https://docs.mem0.ai/api-reference/memory/history-memory); [Mem0 MCP](https://docs.mem0.ai/platform/mem0-mcp)
- No documented field recording the source conversation id / URL / credential per memory (metadata is free-form); memories are extracted facts, not source documents, and no "cite the source" mechanism is documented (gap)

Write safety and authorization

Benchmark claims and critiques
- Paper abstract: 26% relative improvement over OpenAI memory (LLM-as-judge), 91% lower p95 latency, >90% token savings vs full context; its own Table 2: Mem0 66.88, Mem0g 68.44, Zep 65.99, LangMem 58.10, A-Mem 48.38, full-context 72.90 (full context beats every memory system) — [arXiv](https://arxiv.org/abs/2504.19413); [arXiv HTML](https://arxiv.org/html/2504.19413v1)
- Zep rebuttal (2025-05-06): Mem0 assigned the user role to both speakers, embedded timestamps in text, ran searches sequentially; corrected Zep 75.14 vs Mem0g 68.44; lists LoCoMo flaws (16k-26k-token conversations fit in context, no knowledge-update questions, wrong speaker attributions) — [Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Penfield Labs audit: 99/1,540 LoCoMo answer-key errors (6.4%), gpt-4o-mini judge accepts up to 63% of intentionally wrong answers — [dev.to](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- Letta: plain filesystem tools score 74.0% on LoCoMo — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory/)
- Current README claims LoCoMo 92.5, LongMemEval 94.4, BEAM-1M 64.1, BEAM-10M 48.6 (vendor, 2026-10-09) — [GitHub](https://github.com/mem0ai/mem0); Zep claims 94.7% while Mem0's comparison page reports Zep at 80.32% — unresolved conflict — [Zep research](https://www.getzep.com/research/); [Mem0 vs Zep](https://mem0.ai/blog/zep-vs-mem0-which-ai-memory-layer-should-you-choose)

Weaknesses and complaints (2025-2026)
- Issue #4573 junk/feedback loop; telemetry on by default; OSS graph memory removed (Platform upsell); history DB in-memory by default; naive add-per-message "explodes" LLM cost — [issue #4573](https://github.com/mem0ai/mem0/issues/4573); [cost guide](https://theneuralbase.com/mem0/learn/advanced/cost-per-memory-operation/)
- Human-in-the-loop: OpenMemory dashboard pause/archive/delete; plugin `/mem0:pause`, `/mem0:resume`, `/mem0:forget`; no approve-before-write flow anywhere — [OpenMemory blog](https://mem0.ai/blog/how-to-make-your-clients-more-context-aware-with-openmemory-mcp); [Claude Code integration](https://docs.mem0.ai/integrations/claude-code)
- Gaps: GitHub release tag/date; version of the OSS graph-driver removal; score field in search results; per-memory source provenance field; SOC 2/HIPAA/residency; current OpenMemory repo location; HN/Reddit threads not surfaced (search budget exhausted)

Versus SecondBrain (Mem0)
- Memory is DB rows (OSS) or Mem0's cloud, never user-owned Markdown; the most powerful features (graph, Dream, MCP, Claude Code plugin) are hosted-only, so the "agents read and write my brain" role runs through Mem0's cloud.
- Provenance is limited to `actor_id`/`role` in a history table that is in-memory by default; no source link, no credential record.
- Any key holder or MCP client can update and bulk-delete; #4573 shows what unreviewed extraction does at scale. SecondBrain's proposal gate has no counterpart.
- Retrieval is similarity-first with filters and a silently-degrading hybrid; no typed who/when SQL, no degraded-state reporting.
- Local-only operation is possible for the OSS library (Ollama + local store) but opt-out telemetry and the cloud-only MCP undercut it; there is no per-tool scope model.

- `supermemoryai/supermemory-mcp` (1.7k stars, MIT): "MCP v1 is being deprecated", code now in the monorepo `apps/mcp` — [supermemory-mcp](https://github.com/supermemoryai/supermemory-mcp)
- OSS status: the self-hosted server binary is "built from a separate non-public codebase" and free within a "lite license limit"; SDKs and other components are open source — [Self-hosting overview](https://supermemory.ai/docs/self-hosting/overview.md)

Architecture and storage
- Memories "live in an internal graph database"; engine has "Vector, FTS, and graph built in"; hosted stack uses Cloudflare Workers/KV and Postgres — [How it works](https://supermemory.ai/docs/concepts/how-it-works.md); [GitHub](https://github.com/supermemoryai/supermemory)
- Local mode: one binary (`npx supermemory local`), API on `localhost:6767`, data in `./.supermemory`, embedded graph engine, default local embeddings `Xenova/bge-base-en-v1.5` (768-d); on-disk format undocumented — [Self-hosting overview](https://supermemory.ai/docs/self-hosting/overview.md)
- Data model: document (stable `id`, `namespace` as isolation boundary, filterable metadata) to chunks (kept for "SuperRAG" grounding) to memory entries to profile (static + dynamic); memory entry fields include `version`, `isLatest`, `isForgotten`, `isStatic`, `isInference`, `sourceCount`, `parentMemoryId`, `rootMemoryId`, `forgetAfter`, `forgetReason`, `memoryRelations {updates | extends | derives}`, `documentIds[]`, `history[]` — [List memory entries with history](https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history.md)
- Cloud-only: connectors (Google Drive, Notion, Gmail, OneDrive), Supermemory MCP, "proprietary long-horizon extraction models"; Enterprise offers air-gapped self-hosting — [Self-hosting overview](https://supermemory.ai/docs/self-hosting/overview.md); [Pricing](https://supermemory.ai/pricing)

How memories are written and retrieved
- Automatic pipeline (extraction, chunking, embedding, indexing) then "dreaming", where a "custom learning model" merges and organises memories, decides when to forget and creates relations; updates create a new version with `isLatest`; contradictions resolve to the newest fact; "facts persist, episodes decay" — [How it works](https://supermemory.ai/docs/concepts/how-it-works.md); [Graph memory](https://supermemory.ai/docs/concepts/graph-memory.md)
- Claude Code plugin (`claude-supermemory`): Node hooks capture conversations and important tool use, automatic recall each turn, works against the hosted API by default or `npx supermemory local` via `baseUrl` — [Claude Code integration](https://supermemory.ai/docs/integrations/claude-code.md)
- Search: modes `hybrid` (default), `memories`, `chunks`; every result has `similarity` 0-1; `rerank` none | order | aggregate; threshold default 0.3; nested metadata filters (no date filter documented); `include.documents` attaches the source document; limit max 100 — [Search](https://supermemory.ai/docs/recall/search.md)
- Inferred memories are "down-weighted in search until someone confirms them" — [Memory review](https://supermemory.ai/docs/recall/memory-review.md)

Provenance, citations, write safety, authorization
- Per entry: `documentIds`, `sourceCount`, version chain and `history[]`, `spaceId`, `orgId`, timestamps; which agent/credential wrote a memory is not a documented field — [List memory entries with history](https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history.md)
- Review queue exists only for inferred (`isInference: true`) memories: `GET /v3/container-tags/{tag}/inferred`, `POST .../inferred/{memoryId}/review` with approve | decline | undo; the developer builds the UI and the API does not verify a human is behind the call — [Memory review](https://supermemory.ai/docs/recall/memory-review.md)
- Explicit memories: any key holder or OAuth'd MCP client with a writable space can add, update (new version) or forget without approval; MCP `add_memory` has `action: forget` — [Supermemory MCP](https://supermemory.ai/docs/supermemory-mcp/mcp.md)
- Auth: `Authorization: Bearer`; org master key vs scoped keys (`sm_<orgId>_...`) restricted to one namespace and an endpoint allow-list, `expiresInDays` 1-365, rate limit default 500/60 s; no read-only keys documented; Scale plan adds "per-tag access" — [Authentication](https://supermemory.ai/docs/authentication.md); [Pricing](https://supermemory.ai/pricing)

MCP support
- Hosted `https://mcp.supermemory.ai/mcp`, OAuth (user selects which spaces the client may access); tools search_memory, get_profile, add_memory (incl. forget), list_documents, get_document, list_memories, list_spaces, who_am_i; MCP Apps widgets; Claude Desktop and ChatGPT guides; cloud-only (not in Supermemory local) — [Supermemory MCP](https://supermemory.ai/docs/supermemory-mcp/mcp.md); [Self-hosting overview](https://supermemory.ai/docs/self-hosting/overview.md)
- Not in the official MCP Registry under supermemory.ai's name: a search for "supermemory" returns only an unrelated `io.github.YashvantHange/supermemory` project — [registry search](https://registry.modelcontextprotocol.io/v0/servers?search=supermemory&limit=50)

Models, privacy, pricing
- Local: embeddings local (Xenova) or OpenAI/Gemini/Ollama; LLM via a local OpenAI-compatible endpoint; URL ingestion uses a hosted reader service so fully offline use needs text/file inputs; local telemetry on unless `SUPERMEMORY_DISABLE_TELEMETRY=1` — [Self-hosting overview](https://supermemory.ai/docs/self-hosting/overview.md); [Providers](https://supermemory.ai/docs/self-hosting/providers.md)
- Security page: SOC 2 Type II, HIPAA BAA on Scale/Enterprise, GDPR, "customer content is never used to train models"; no regions listed — [Security](https://supermemory.ai/docs/overview/security.md)
- Pricing (2026-10-09): Free $0 with $5 credits/mo; Pro $19/mo ($20 credits); Max $100/mo ($130 credits); Scale $399/mo ($600 credits, SOC 2, HIPAA BAA, self-hosting); Enterprise custom; metered memory $0.005 per 1K "SM tokens" text, search $0.005 per 1K queries — [Pricing](https://supermemory.ai/pricing)

Weaknesses and gaps
- Closed-source server; MCP and connectors cloud-only; rapid API churn (v3/v4/v5) with doc inconsistencies; black-box "custom learning model"; third-party reviews cite cost growth and lock-in; no HN/Reddit threads surfaced — [gamgee comparison](https://gamgee.ai/vs/supermemory-vs-retaindb/); [aicoolies review](https://aicoolies.com/reviews/supermemory-review)
- Gaps: HQ; any 2026 round; the "Memory Router"/"Infinite chat" proxy is absent from the current docs index (likely retired/renamed, unconfirmed); Chrome extension current status; Obsidian/Markdown sync (not in docs); dedup rules; on-disk format and licence text of the "lite" binary; MCP transport name

Versus SecondBrain (Supermemory)
- Strongest competitor on revision provenance (version chain, `history[]`, `documentIds`, `isInference` down-weighting) but memory still lives in an opaque graph store behind a closed binary or the hosted service, not in files the user owns.
- Its review queue is the closest analogue to `brain_update` proposals, yet it gates only inferred memories, is API-only, and cannot prove a human approved.
- Retrieval is similarity-first with metadata filters and no date filter; no SQL over typed people/time properties.
- Local mode exists but MCP is cloud-only, telemetry is opt-out, and there is no per-tool read/write/infer/admin split or read-only key.

Architecture and storage

### Inferences
- The market has bifurcated: hosted "memory APIs" (Mem0 Platform, Supermemory, Zep Cloud, Honcho, Memori Cloud, claude-mem Pro) monetise extraction and retrieval per token/credit, while the open-source cores are being thinned (Mem0 removed OSS graph memory; Zep deprecated CE; Supermemory's server is closed; Letta retired its V1 server). Self-hosters are increasingly left with libraries, not products.
- Every system that extracts memories with an LLM has a documented failure of unreviewed writes at scale in 2026 (Mem0 #4573, Graphiti #1728, Letta #4930, Basic Memory's 2026 data-loss bugs even without extraction). A proposal-and-approve gate is not a nicety; it addresses the most-reported class of failure.
- The two file-native systems (Letta MemFS, Basic Memory) prove that "agent writes Markdown the user owns" is viable with Claude Code and Claude Desktop today; their gaps are exactly SecondBrain's claimed differentiators (typed properties, provenance per write, scoped credentials, approval).
- Benchmark numbers (LoCoMo, LongMemEval) are vendor-contested and the datasets are flawed; they should not drive a comparison, but their existence shows what buyers ask for.
- Registry presence is a weak but real maturity signal: Basic Memory, Mem0 and Letta publish there; Cognee, Zep and Supermemory do not.

## KQ3: Which record provenance (which agent/credential created a memory) and keep revisions, versus overwriting?

### Takeaway

No studied product requires human approval for an agent's write, overwrite or delete; the closest mechanisms are Supermemory's API-only review queue for inferred memories, Zep Cloud's per-connection read-only toggle and account kill switch, Basic Memory's overwrite-refusal default, Gemini CLI's experimental Auto Memory inbox (patches applied only after `/memory inbox` approval) and the hobby project graphiti-local (read-only MCP, human-reviewed ingestion). ### Cited Findings

- Letta: agents commit/push autonomously; "Agent reviews before applying" "does not ask for your approval"; hosted MCP runs "without approval prompts" — [Letta Code memory](https://docs.letta.com/letta-code/memory); [Hosted MCP](https://docs.letta.com/platform/hosted-mcp/index.md)

### Inferences
- A server-side proposal that only an interactive human session can approve (SecondBrain's `brain_update`) is stronger than every competitor's model, which at best relies on the MCP client's permission prompt or a toggle an agent cannot flip.

### Gaps
- Supermemory's consumer app UI for approvals was not verified.

## KQ5: Which support structured/temporal queries ("decisions last month", "who said what when") beyond similarity search?

### Takeaway

## KQ7: What are the per-tool authorization and scoping capabilities in each system, and in MCP generally?

### Takeaway
MCP defines authorization only at the HTTP transport (OAuth 2.1, server-defined scope strings, step-up via `insufficient_scope`) and explicitly leaves per-tool permission to the server ("Implement proper access controls") and the client (confirmation prompts, Claude Code's `mcp__server__tool` allow/deny rules); among memory products, only Zep Cloud (per-connection read-only, ABAC on API keys), Supermemory (namespace-scoped keys with endpoint allow-lists, OAuth space selection) and Letta's App Server (capability tokens) go beyond a single all-powerful key, and none offers a read/write/infer/admin split per tool.

### Cited Findings
- MCP core: authorization "at the transport level" for HTTP; stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment"; scopes via `WWW-Authenticate` challenges with step-up; `tools/list` "MAY vary by the authorization presented on the request"; servers MUST "Implement proper access controls" — [Authorization (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- MCP extensions: Enterprise-Managed Authorization centralises which servers a user may reach via IdP-issued ID-JAG tokens; OAuth Client Credentials for machine-to-machine; neither adds per-tool permissions — [Enterprise-Managed Authorization](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization); [ext-auth](https://github.com/modelcontextprotocol/ext-auth)
- Claude Code client-side: `mcp__<server>__<tool>` in allow/deny/ask rules; `_meta["anthropic/requiresUserInteraction"]` forces a prompt; enterprise `allowedMcpServers`/`deniedMcpServers` — [Claude Code MCP](https://code.claude.com/docs/en/mcp); Gemini CLI `includeTools`/`excludeTools` per server — [Gemini CLI MCP](https://geminicli.com/docs/tools/mcp-server/); ChatGPT OAuth 2.1 only, "does not support machine-to-machine grants" — [Apps SDK full text](https://developers.openai.com/apps-sdk/llms-full.txt)
- Mem0: project API keys, OWNER/READER members, no read-only key, no per-tool permissions — [Orgs and projects](https://docs.mem0.ai/api-reference/organizations-projects)
- Supermemory: scoped keys limited to one namespace and an endpoint allow-list; OAuth space selection in MCP; no read-only key — [Authentication](https://supermemory.ai/docs/authentication.md); [Supermemory MCP](https://supermemory.ai/docs/supermemory-mcp/mcp.md)
- Letta: Admin/Editor/Analyst roles; tool permissions per connected computer; App Server capability or signed bearer tokens — [Teams permissions](https://docs.letta.com/teams/permissions/index.md); [App Server quickstart](https://docs.letta.com/self-hosting/app-server/quickstart/index.md)
- Zep: project keys, ABAC policies on keys, per-connection read-only MCP; "Your application must enforce its own tool and action permissions"; Graphiti OSS MCP has no auth — [Governance](https://help.getzep.com/governance); [Memory MCP server](https://help.getzep.com/v3/memory-mcp-server); [Graphiti MCP README](https://github.com/getzep/graphiti/tree/main/mcp_server)
- Cognee: dataset-level grants and tenant roles; MCP "no client login", optional `API_TOKEN` — [cognee-mcp README](https://github.com/topoteretes/cognee/tree/main/cognee-mcp)
- Basic Memory: no local auth; cloud OAuth + roles; no per-tool scopes — [MCP tools reference](https://docs.basicmemory.com/raw/reference/mcp-tools-reference.md)
- Honcho, Memori, Hindsight, mcp-memory-service: API-key or OAuth gateways; Hindsight MCP "unauthenticated by default" (third-party) — [Honcho](https://github.com/plastic-labs/honcho); [Mnemoverse comparison](https://mnemoverse.com/docs/library/memory-mcp-servers-compared)

### Inferences
- Because the protocol sanctions scope-filtered `tools/list` and `insufficient_scope` challenges, SecondBrain can expose its read/write/infer/admin matrix in a standards-conformant way (read-only bridge keys see only read tools) and still be unusual in the category.

### Gaps
- Whether any competitor binds authorization into background jobs started by a tool call (SecondBrain's "initiating credential" requirement) was not documented anywhere.

## KQ9: What is the actual state of the Model Context Protocol in 2026 (revision, transports, authorization, registry, governance, adoption)?

### Takeaway
The current MCP revision really is `2026-07-28` (released 2026-07-28, preceded by `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`): it made the protocol stateless (no `initialize` handshake, no `Mcp-Session-Id`, no GET/SSE resumption), replaced server-initiated requests with Multi Round-Trip Requests, formally Deprecated the 2024-11-05 HTTP+SSE transport plus Roots, Sampling, Logging and Dynamic Client Registration, and moved Tasks into an extension. Authorization is OAuth 2.1 at the HTTP transport level only (stdio servers are told to use environment credentials); the core protocol defines no per-tool permission primitive — scopes are server-defined strings surfaced through `WWW-Authenticate` challenges, `tools/list` may legally vary with the caller's scopes, and human-in-the-loop confirmation is a client-side SHOULD. The registry is still "preview"; governance moved to the Linux Foundation's Agentic AI Foundation on 2025-12-09.

### Cited Findings

Revision history and what changed, 2025-2026 (all primary, modelcontextprotocol.io):
- The current protocol version is `2026-07-28`; versions are `YYYY-MM-DD` strings marking the last backwards-incompatible change; revisions are Draft, Current or Final; every request now declares its version in `_meta` (`io.modelcontextprotocol/protocolVersion`) and, on Streamable HTTP, in the `MCP-Protocol-Version` header; a server that does not support the version returns `UnsupportedProtocolVersionError`; `server/discover` is a mandatory server RPC that clients MAY call; handshake-based revisions are "`2025-11-25` and earlier" — [MCP Versioning](https://modelcontextprotocol.io/specification/versioning)
- `2026-07-28` major changes: (1) remove protocol-level sessions and `Mcp-Session-Id` (SEP-2567); (2) remove the `initialize`/`notifications/initialized` handshake, carry version/capabilities/clientInfo per request in `_meta` (SEP-2575); (3) add mandatory `server/discover`; (4) replace the HTTP GET stream and `resources/subscribe` with `subscriptions/listen`; (5) remove `ping`, `logging/setLevel`, `notifications/roots/list_changed`; (6) move Tasks out of core into the `io.modelcontextprotocol/tasks` extension with polling `tasks/get` (SEP-2663); (7) Multi Round-Trip Requests replace server-initiated `roots/list`, `sampling/createMessage`, `elicitation/create` with `resultType: "input_required"` results (SEP-2322); (8) all results carry a required `resultType`; (9) remove SSE resumability and `Last-Event-ID` — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- `2026-07-28` minor changes: `extensions` field in capabilities; OpenTelemetry `traceparent`/`tracestate`/`baggage` in `_meta` (SEP-414); deterministic `tools/list` ordering SHOULD; required `Mcp-Method`/`Mcp-Name` headers on Streamable HTTP POSTs plus `x-mcp-header` parameter mirroring (SEP-2243); required `ttlMs`/`cacheScope` on list and read results (SEP-2549); resource-not-found code changed `-32002` to `-32602`; RFC 9207 `iss` validation (SEP-2468); `application_type` required in DCR (SEP-837); credentials keyed by issuer (SEP-2352); any JSON Schema 2020-12 keywords allowed in `inputSchema`/`outputSchema` (SEP-2106); error-code allocation policy reserving `-32020` to `-32099` for the spec — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- `2026-07-28` deprecations: Roots, Sampling and Logging (SEP-2577, "remain fully functional during the deprecation window"); HTTP+SSE transport "deprecated since protocol version `2025-03-26`" reclassified as Deprecated (SEP-2596); `includeContext` `"thisServer"`/`"allServers"`; OAuth Dynamic Client Registration deprecated in favour of Client ID Metadata Documents (PR #2858) — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- Deprecated-features registry (2026-07-28): Roots, Sampling, Logging and DCR deprecated in `2026-07-28`, earliest removal "First revision released on or after 2027-07-28"; HTTP+SSE deprecated `2025-03-26`, earliest removal "Three months after SEP-2596 reaches Final"; `includeContext` values deprecated `2025-11-25`; "No features have been removed under this policy yet" — [Deprecated Features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
- Feature lifecycle policy: deprecated features stay in the spec at least twelve months (ninety days under expedited removal) before becoming eligible for removal — [MCP Versioning](https://modelcontextprotocol.io/specification/versioning)
- `2025-11-25` (predecessor `2025-06-18`) major changes: OpenID Connect Discovery for authorization-server discovery (PR #797); icons for tools/resources/prompts (SEP-973); incremental scope consent via `WWW-Authenticate` (SEP-835); tool-name guidance (SEP-986); enum elicitation (SEP-1330); URL-mode elicitation (SEP-1036); tool calling in sampling (SEP-1577); OAuth Client ID Metadata Documents as recommended client registration (SEP-991); experimental Tasks (SEP-1686); plus SDK tiering (SEP-1730), governance formalisation (SEP-932), working groups (SEP-1302), JSON Schema 2020-12 default (SEP-1613), RFC 9728 alignment (SEP-985), SSE polling via server disconnect (SEP-1699) — [2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- `2025-06-18` (predecessor `2025-03-26`) major changes: removed JSON-RPC batching (PR #416); structured tool output (PR #371); MCP servers classified as OAuth Resource Servers with Protected Resource Metadata (PR #338); RFC 8707 resource indicators required (PR #734); elicitation (PR #382); resource links in tool results (PR #603); `MCP-Protocol-Version` header required on HTTP (PR #548); `_meta`, `title`, completion `context` fields — [2025-06-18 changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- `2025-03-26` (predecessor `2024-11-05`) major changes: OAuth 2.1 authorization framework (PR #133); HTTP+SSE replaced by Streamable HTTP (PR #206); JSON-RPC batching added (PR #228, later removed); tool annotations such as read-only/destructive (PR #185); audio content; `completions` capability — [2025-03-26 changelog](https://modelcontextprotocol.io/specification/2025-03-26/changelog)
- Release post (2026-07-28, by lead maintainers David Soria Parra and Den Delimarsky): describes the shift "from a bidirectional stateful protocol into a request/response stateless protocol"; TypeScript, Python, Go and C# SDKs "all speak `2026-07-28` as of release", Rust in beta, FastMCP 4.0 mentioned; "close to half a billion downloads a month across the Tier 1 SDKs", TypeScript and Python SDKs "each passed 1 billion total downloads"; the release "includes breaking changes" and gives no end-of-support date for older revisions — [The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

Streamable HTTP transport as of 2026-07-28 (relevant to a self-hosted server):
- Single MCP endpoint accepting POST; each JSON-RPC request is its own POST; response is one JSON object or a request-scoped SSE stream; server-to-client interactions are embedded as MRTR input requests; long-lived change notifications come through a `subscriptions/listen` response stream; `Last-Event-ID` resumption "not supported"; closing the SSE response stream is the cancellation signal — [Streamable HTTP (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Security: servers MUST validate `Origin` and respond 403 to invalid origins (DNS-rebinding defence); local servers SHOULD bind to 127.0.0.1; servers SHOULD implement authentication — [Streamable HTTP (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Required headers: `MCP-Protocol-Version` (must match `_meta`, else 400 + `HeaderMismatch` `-32020`), `Mcp-Method` on all requests, `Mcp-Name` on `tools/call`/`resources/read`/`prompts/get`; servers that process the body MUST reject header/body mismatches; a 2026-07-28-only server SHOULD answer GET/DELETE with 405, ignore `Mcp-Session-Id` and `Last-Event-ID` — [Streamable HTTP (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Backward compatibility: clients MAY probe with a modern request and fall back to `initialize` on a 400 whose body is not a recognised modern JSON-RPC error; legacy HTTP+SSE detection is by GET expecting an `endpoint` event — [Streamable HTTP (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Stateful tools guidance (non-normative): "MCP has no protocol-level session"; state across calls is carried by explicit server-minted handles passed as ordinary tool arguments; for authenticated servers "a handle is a name, not a capability" and authorization must be re-validated per call — [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

Authorization and per-tool permissions in MCP generally:
- Authorization is OPTIONAL and "at the transport level"; HTTP transports SHOULD conform; "Implementations using an STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment" — [Authorization (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- MCP server = OAuth 2.1 resource server; MUST implement RFC 9728 Protected Resource Metadata; clients MUST send RFC 8707 `resource` parameters and MUST support both RFC 8414 and OIDC discovery; MUST obtain a client ID via Client ID Metadata Documents, pre-registration or (deprecated) DCR; tokens MUST be bearer tokens in the `Authorization` header, never in query strings; servers MUST validate audience — [Authorization (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Scopes: servers SHOULD put a `scope` parameter in the 401 `WWW-Authenticate` challenge (example `scope="files:read"`); runtime insufficient-scope errors are 403 with `error="insufficient_scope"` and `scope="files:write"`-style guidance; clients SHOULD step up by requesting the union of previously granted and challenged scopes; "Servers MUST account for scope hierarchies"; scope names themselves are entirely server-defined — [Authorization (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- The core protocol has no per-tool authorization primitive; the closest statements are that `tools/list` "MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit", that servers MUST "Implement proper access controls", and that clients MUST "consider tool annotations to be untrusted unless they come from trusted servers" — [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Human in the loop is a client-side SHOULD: "there SHOULD always be a human in the loop with the ability to deny tool invocations"; applications SHOULD show which tools are exposed, indicate invocations, and "Present confirmation prompts to the user for operations"; clients SHOULD "Prompt for user confirmation on sensitive operations", show tool inputs before calling, and "Log tool usage for audit purposes" — [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Tool execution errors (`isError: true`) are the channel for actionable failures such as validation errors so the model can self-correct; protocol errors are JSON-RPC errors — [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Authorization extensions (optional, additive, composable, independently versioned) live in the `ext-auth` repository: Enterprise-Managed Authorization (Stable) and OAuth Client Credentials (Draft); MIT licence; 167 stars, 54 forks, no releases (2026-10-09) — [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth)
- Enterprise-Managed Authorization (`io.modelcontextprotocol/enterprise-managed-authorization`, origin SEP-990): the enterprise IdP issues an Identity Assertion JWT Authorization Grant (ID-JAG) that the client exchanges at the MCP authorization server; it centralises which servers employees may reach and revocation, and says ID-JAG "tokens may have scope restrictions" — it does not add per-tool permissions — [Enterprise-Managed Authorization](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)
- Local (stdio) server security guidance (new in the 2026-07-28 docs): "the client and a stdio server share one trust domain"; "The stdio transport is not a sandbox"; recommends per-server narrowly scoped tokens, read-only directory grants, containers with `--network=none` where possible, pinned versions, and warns that "Binding to 127.0.0.1 is not an authentication boundary" for local bridges that listen on a port; SEP-1024 requires one-click installers to show the exact command — [Local Server Security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)

### Inferences
- SecondBrain's per-tool read/write/infer/admin scopes are an application-layer design, not something MCP gives for free; the spec explicitly allows a scope-filtered `tools/list` and `insufficient_scope` challenges, so the design is protocol-conformant but every competitor's "authorization" claims must likewise be read as application-level, because no MCP memory server can inherit per-tool permissions from the protocol.
- The spec places confirmation of destructive calls on the client (SHOULD), and memory servers that rely on client prompts are only as safe as the client's permission mode; a server-side proposal queue such as `brain_update` is strictly stronger than what the protocol requires.
- A stdio bridge (`brain mcp`) that reads a stored key from the environment and forwards to a stateless HTTP daemon is the pattern the spec recommends for stdio (environment credentials, no OAuth), and the local-server-security guide's warning about local bridges listening on ports argues for keeping the bridge a pure stdio forwarder.
- Because `tools/list` must not vary per-connection but may vary by presented credential, read-only bridge keys can legitimately see only read tools; this is now sanctioned behaviour rather than a workaround.
- The HTTP+SSE deprecation means memory servers whose MCP endpoint still advertises only `/sse` (several 2025-era projects did) are on a removal path; this is a concrete maturity signal to check per competitor.
