# Write-approval model review (Grok 4.7, reasoning xhigh, 2026-10-09)

Reviewed against spec Draft v0.6 (dated 2026-10-08) and the uncommitted working tree as read on 2026-10-09. Line numbers below are from that read; identifiers are the stable names. Web sources were fetched the same day. Claims taken only from `reports/` and `research_notes/` and not re-opened are marked unverified.

## Overall assessment

The owner's objection is right, and the current mitigation does not answer it. D10, ING-12, CHAT-6 and SEC-12 send every body, type, property, tag-removal and delete from a write key or from the assistant through an interactive approval. `assistant.auto_approve_writes` is off, and on a real chat turn it cannot turn on: §7.3 makes retrieval part of the turn, and CHAT-6 withdraws auto-approve as soon as any document, neighbor or document-backed compaction is in the execution record. The risk-register row "Approval fatigue leads to auto-approve" describes a control that the chat path never reaches. People will rubber-stamp the queue or stop saving. The field already did both.

The replacement should not be "apply every write, glance later" and it should not be "hold every write that followed a read." The operation that turns untrusted retrieved text into a cited fact is a rewrite of a document the actor did not create, performed in a turn that read documents. That one class stays a proposal. Everything else the owner actually does — Claude Code saving a decision, a nightly transcript upsert into a folder the owner named, the assistant filing a note into its own lane — should apply at once as an ordinary attributed revision, with a one-click revert that refuses to clobber a later human edit.

Candidate A ("apply now, review after") has the right default posture and the right single hold, and then gives every write key the rest of the vault. Appends, tag removal, type and property changes, and soft-deletes of documents the agent did not create still land after a read. A fading badge is not a boundary. Candidate B ("explicit capabilities plus provisional revisions") has the right authorization primitive — a standing grant the human authors in settings, with step-up, never by clicking a card and never by the model — and the wrong lifecycle. Auto-confirm after a window is silent acceptance, and keeping every post-retrieval write as a proposal recreates the queue the owner rejected.

Recommended design: **granted lanes**. A credential may immediately create, append, edit and soft-delete only where a session has granted a capability. Those writes are real revisions, searchable and citable, marked `unreviewed`, and reverted by a new revision. The clock never promotes them to `confirmed`. Tainted body replacement, and any mutation outside the lane, remains a proposal that only a browser or paired-CLI session can approve. Purge, credentials, capability grants, sources, the type registry, and the review mode stay behind step-up. `writes.review: before` remains available and defaults to `after`.

## Research

Method: primary pages and papers fetched on 2026-10-09, plus the two reports and their notes in this repo. Where a page would not return a body, the finding says so.

### Post-hoc review in systems that already have a canonical document

**Git.** Safety on a shared branch is a gate before the commit becomes the branch people read, plus a revert after the fact. A revert is a new commit whose tree restores an older tree; it does not delete history, and it conflicts when later commits touched the same lines. Protected-branch pull requests are pre-merge review of a side branch. They are a poor template for a vault whose live file is the thing search cites. The part worth copying is the revert: a new revision, an explicit parent, and a refusal to overwrite divergent later work. [Pro Git, undoing things](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things).

**Wikipedia.** Two different mechanisms are easy to conflate. Pending-changes protection, level 1, stores the edit and shows anonymous readers the last accepted revision until a reviewer accepts it. Reviewers are told they do not certify correctness, only that the edit is not obvious vandalism, a living-person violation, or a copyright problem. Patrolled revisions, the model that was proposed and not shipped with the English trial, mark a revision after it is already what readers see and do not change the displayed page. [Pending changes](https://en.wikipedia.org/wiki/Wikipedia:Pending_changes), [Reviewing pending changes](https://en.wikipedia.org/wiki/Wikipedia:Reviewing_pending_changes), [Patrolled revisions](https://en.wikipedia.org/wiki/Wikipedia:Patrolled_revisions) (pages current as fetched 2026-10-09). For a single owner who is both writer and reader, pending changes hide the note from the only person who would use it. Patrolled revisions plus revert match an activity feed. They do not, by themselves, limit who may edit.

**Google Docs suggestion mode and version history.** Suggesting mode records a proposal anchored to the current text; the document bytes change when the owner accepts. Editing mode changes the bytes immediately, and version history is the undo. The two are different products. An agent that "suggests" is Candidate B's proposal. An agent that edits, with history, is Candidate A's apply-now. Docs does not auto-accept suggestions on a timer. [Suggest edits in Google Docs](https://support.google.com/docs/answer/6033474) (longstanding product behavior; the help page was not re-opened in this pass).

**Notion.** Human suggestion mode (shipped 2024-07-29) leaves the page unchanged until accept or reject. The Agent has a separate approval control: Always ask, Review for me (the documented default, which asks on actions judged unsafe), and Skip all approvals. Reading does not require approval. On 2026-08-28 Notion shipped "Ask your agent to suggest edits," so the agent can be put back into the suggestion protocol per request. [Suggested edits](https://www.notion.com/help/suggested-edits), [Choose how Notion AI asks](https://www.notion.com/help/choose-how-notion-agent-asks-for-your-approval), [release note 2026-08-28](https://www.notion.com/releases/2024-07-29). The useful split is per-action class, not one switch for every write. "Review for me" is a model judging risk. SecondBrain's SEC-14 forbids that as a boundary.

**Tana.** Write tools, including MCP writes from Claude, create proposals attached to a session. The user reviews them in Tana. The agent can call `approveProposals`, and the server also accepts `autoApprove: true` when the user has already chosen to skip review (a CLI flag such as `--approve` is the documented example). "Asking the agent to make a change does not count as skipping review." [Tana MCP](https://tana.inc/learn/features/mcp), [Proposals](https://tana.inc/learn/features/proposals.md) (fetched 2026-10-09). Tana still added restore for soft-deleted documents because deletions happen by mistake; the 2026-05-08 changelog is "Restore deleted documents," and the 2026-06-05 post repeats a Restore control on the deleted-doc panel. [Changelog 2026-05-08](https://tana.inc/changelog/2026-05-08-meeting-digest), [Tana takes it from here](https://tana.inc/blog/tana-takes-it-from-here). Proposals did not remove the need for trash. An `autoApprove` bit on the write call is the hole: the model can be talked into passing it. A grant has to live in settings, checked by the server, not in a tool argument.

### How agent products actually let writes through

**Claude Code.** `CLAUDE.md` is instructions the user writes and the tool loads. Auto memory is a directory the model writes, `~/.claude/projects/<project>/memory/`, one folder per repository, machine-local. The first 200 lines or 25 KB of `MEMORY.md` load every session. Files are plain markdown the user can edit or delete. There is no approval step. [Claude Code memory](https://code.claude.com/docs/en/memory) (docs fetched 2026-10-09, page dated in the index as recently updated). This is the interaction Claude Code users already expect of `brain_remember`: a file appears, attributed, and the user deletes it if it is wrong. It is also how a poisoned note becomes the next session's instructions. The 200-line cap limits blast radius. It does not review content.

**GitHub Copilot Memory.** Public preview. Stores repository facts and personal preferences. For org-managed plans it is off until an admin enables it; for individual paid plans it is on and the user may opt out. Unused entries are deleted after 28 days, and the timer resets when an entry is used. Repository owners can delete entries. Capture includes facts taken from pull requests that were closed without merging. [About Copilot Memory](https://docs.github.com/copilot/concepts/agents/copilot-memory), [Manage as administrator](https://docs.github.com/copilot/how-tos/use-copilot-agents/copilot-memory/manage-as-administrator). There is no per-write approval. Expiry is the control, and use refreshes it, so a fact the agent keeps citing never expires. That is the wrong control for a vault, where the point of a note is to be cited.

**Gemini CLI Auto Memory.** Experimental, off unless `experimental.autoMemory` is true. A background pass reads local transcripts and writes unified-diff patches into a project-local inbox. Nothing is applied until `/memory inbox`. The pull request that added the flow removed an `autoApply` mode: "auto-memory is review-only." [docs/cli/auto-memory.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/auto-memory.md), [PR 26338](https://github.com/google-gemini/gemini-cli/pull/26338). This is the right shape for unsolicited extraction. SecondBrain's assistant does not mine the corpus overnight; it writes when a turn asks to save, or when a script posts. An inbox for every such write is the queue the owner will not use. An inbox for memories nobody asked to store is still right, and SecondBrain should keep not auto-extracting.

**Supermemory.** Stated facts are stored. Facts the graph infers are `isInference: true` and down-ranked in search until a person approves them. Decline sets `isForgotten` and removes them from search. Undo returns them to the queue. There is no timer that clears the flag. [Review inferred memories](https://supermemory.ai/docs/recall/memory-review) (fetched 2026-10-09). Down-rank until a positive confirm is the pattern to copy for agent writes that were derived from retrieved documents. A timer is not.

**Letta.** Memory is a git checkout (MemFS). Reflection subagents edit a worktree and are instructed to merge and push on their own. The prompt's conflict rule prefers the reflection branch's content for memory files. [Letta memory docs](https://docs.letta.com/letta-code/memory/), [MemFS](https://docs.letta.com/letta-code/memfs/), [PR 940](https://github.com/letta-ai/letta-code/pull/940). Issue [#4930](https://github.com/letta-ai/letta-code/issues/4930), opened 2026-10-03, is titled "Let SDK clients approve reflection merges before they land (`merge: "client"`)." The issue body did not load in this pass (GitHub returned an interstitial). The title plus PR 940 are enough to say the default path merges without a client gate. The research notes' anecdote that a specific harmful reflection was auto-merged is **not verified here**. A 2026-08-16 reading of Letta's block history ([letta#3431](https://github.com/letta-ai/letta/issues/3431)) found undo/redo methods with no production caller outside tests. Git history is not a review step if the merge is autonomous and the undo stack is empty.

**Obsidian agent plugins.** The comparison report, from this repo's 2026-10-09 notes, describes Copilot for Obsidian v4 embedding Claude Code and Codex in the vault, and the Local REST API plugin taking the MCP role. Those plugins write the vault files directly. This review did not re-open the plugin repos. The architectural point stands from the spec's own goal: the vault is the canonical document, so an MCP broker is the only place a policy can run. A plugin that writes files through the watcher is the registered-folder door, which is already automatic and must stay out of the agent-approval queue.

**Always-on agents, from the 2026-10-09 notes, spot-checked where listed.** Hermes documents `write_approval` (default off) staging memory writes, and `trust: untrusted` forcing a client prompt on write-capable MCP tools. Grok Bot's own docs, as quoted in the notes, expire unattended approval cards after about ten minutes and do not review memory writes; "Always allow" stores a rule. Meta's Sentinel is an egress and permission gate outside the model, with grants bound to connector, destination and use case; help text also offers "Always allow," and the grant surface shrinks because Muse "learns over time which decisions need your sign off." A press account (SAN, via the notes) says a tester's "allow always" grant led Muse to give a Marketplace buyer a home address. That incident is **press, not a Meta postmortem**; the design lesson does not depend on it: a standing grant created from a card, then widened by the product, is how a later call exceeds what the user thought they allowed. OpenAI Dots: an eesel.ai review scores day-to-day friction 2.5/5, and HN comments say per-call approval trains people to say yes. The 2.5 figure is **a secondary review, not an OpenAI measurement**. OpenClaw advisory titles "Reusable exec approvals could authorize changed arguments" and "Memory tools could retain revoked access" are **as recorded in the research notes**, citing the GitHub advisory list; this pass did not re-open each advisory. The titles match failures this spec must close: a grant must bind arguments, and revocation must fail a prepared write.

**MCP, 2026-07-28.** Hosts SHOULD keep a human able to deny tool calls. That SHOULD is on the client. The protocol "does not mandate any specific user interaction model." Tool annotations are hints. Clients MUST treat them as untrusted unless the server is trusted. `readOnlyHint` defaults to false, `destructiveHint` defaults to true. [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema). A SecondBrain server that sets `readOnlyHint: true` on a writing tool would be asking Hermes's trust gate to look away. The server's matrix has to be true even when the client prompts, and true when the client does not.

### Memory poisoning and undo

**MINJA** (Dong et al., arXiv:2503.03704, submitted 2025-03-05; HTML of v3 fetched 2026-10-09) injects records through ordinary queries. Reported averages: about 98.2% injection success, about 76.8% attack success, on agents that store and later retrieve those records. The attacker never has a direct memory-write API. A write tool makes the same attack shorter.

**AgentFlayer** (Zenity, Black Hat, 2025-08-06) hid instructions in a document. A normal summarize caused ChatGPT's connectors to search Drive and exfiltrate secrets, including a bypass of the first URL filter. The same research line planted instructions that persist into later sessions. [WIRED](https://www.wired.com/story/poisoned-document-could-leak-secret-data-chatgpt/), [Zenity](https://labs.zenity.io/post/agentflayer-chatgpt-connectors-0click-attack-5b41). For this daemon the exfiltration leg is already constrained (no shell, no network, read caps, egress manifest). The remaining leg is persistence: the model reads a poisoned note and writes another note that search will cite next week.

**Tainted Memories** (LayerX, reported 2025-10-27) is a claimed CSRF that writes hidden instructions into ChatGPT memory. Press coverage the same week treats the persist-across-sessions property as the harm. Later write-ups say OpenAI could not reproduce the Atlas-specific claim. [The Register, 2025-10-27](https://www.theregister.com/2025/10/27/atlas_vulnerability_memory_injection/). Cite it as a reported technique whose reproducibility OpenAI disputed, not as a confirmed Atlas bug. The design point that survives the dispute: a memory write is a durable instruction channel, so the write path needs an origin check the model does not perform.

**Lethal trifecta.** Simon Willison, 2025-06-16, names private data, untrusted content, and external communication. His 2025-11-02 note is explicit that the trifecta covers exfiltration and that tool-using agents have further harms the trifecta does not. [2025-11-02](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/). SecondBrain's assistant has private data and untrusted documents and, by design, no external send. The harm left inside the boundary is corrupting the store the next answer will cite. SEC-14 already says injection resistance is a mitigation. A policy that applies a tainted rewrite because the model asked is the model acting as the boundary.

**OWASP Top 10 for Agentic Applications, version 2026, published December 2025.** ASI06 is Memory and Context Poisoning: corrupt a store once, bias later sessions. Secondary walkthroughs list provenance, quarantine, expiry of unverified memory, and rollback as the controls. ASI09 is human-agent trust exploitation, which is what an Always-allow card trains. The official PDF was not re-downloaded in this pass; the identifier and the December 2025 date are consistent across the secondary pages fetched. [Lineation summary](https://lineation.ai/owasp-top-10-agentic/), [DeepintShield walkthrough](https://deepintshield.com/owasp-agentic-asi-top-10/).

**What automatic memory does in production.** Mem0 issue [#4573](https://github.com/mem0ai/mem0/issues/4573) (2026-03-27): a hand audit of 10,134 extracted memories classified 97.8% as junk. Switching the extractor to a stronger model did not fix the class of failure. Graphiti issue [#1728](https://github.com/getzep/graphiti/issues/1728) (2026-08-04): in one graph of about 3,950 facts, 1,616 (41%) carried `invalid_at`. A four-row hand audit found three of four retirements were collateral; the author marks the sample as too small to characterize the rest. PR 1729's follow-up count, on an earlier snapshot, attributed most retirements to edges that could not plausibly replace the victim. Both are one-operator audits, not vendor benchmarks. They are the right order of magnitude for "the write path believed the model."

**Undo literature, applied narrowly.** Saltzer and Schroeder (1975) put psychological acceptability next to complete mediation and least privilege: a mechanism people bypass is not a mechanism. Brown and Patterson, "Undo for Operators" (USENIX 2003), show that operator undo has to name dependencies and refuse a rollback that would destroy later legitimate work; a blind inverse is not undo. Sagas (Garcia-Molina and Salem, 1987) make the same point for long-running work: compensation is its own forward operation. [Undo for Operators, USENIX](https://www.usenix.org/legacy/events/usenix03/tech/full_papers/brown/brown_html/index.html). Mass revert in this daemon is an operator undo. It has to be specified as one, not as "put the old bytes back."

### What the evidence does and does not support

Supports: pre-approval of every mutation is abandoned in products people actually leave running; the failure mode of that abandonment is a standing grant that is wider than the user remembers, plus memory writes that were exempt from the grant; unreviewed model writes accumulate junk and silently retire good facts; the durable fix in the systems that took it seriously is a human-authored allow-list, a visible unconfirmed flag that does not expire into "confirmed," and a revert that is a new version.

Does not support: a second copy of the document called "provisional" that becomes canonical when a timer fires; hiding agent notes from search until review (the owner will not review, and then the notes do not exist); setting `readOnlyHint` so a careful MCP client stops asking (the hint is advisory, and lying to it is how a trusted-looking server skips the client's SHOULD).

## Findings

1. **Critical — The chat auto-approve rule cannot fire on a turn that does the product's job.**
   **Concerned:** D10; CHAT-6; §7.3 `POST /chat` ("Retrieval is inherent to a turn"); §10.2 read caps ("counting the initial retrieval"); Appendix B `assistant.auto_approve_writes`; §21 "Approval fatigue leads to auto-approve"; M2-G10.
   **Scenario:** The owner asks the assistant, in the UI, to file a decision after a normal question. The turn has already run initial retrieval, or a neighbor expansion, or a compaction that names document ids. The executor, reading the execution record, withholds auto-approve even if the flag is on. U8 ("save this under #woodworking") joins the same queue as soon as the paste shares a turn with any retrieved chunk. The 72-hour proposal expiry then drops the save. The owner stops approving. The risk-register mitigation never ran.
   **Recommendation:** Delete auto-approve-by-absence-of-retrieval as the usability path. Replace it with the lane in the recommended design: a clean or tainted turn may create and append inside the assistant lane immediately. Keep the execution-record test, and use it only to mark `derived` and to hold rewrites of documents the assistant did not create.

2. **Critical — Apply-now without a lane makes a retrieved document the author of the next cited fact.**
   **Concerned:** SEC-14; CHAT-4; ING-12 rows for append, type, properties, tag removal, and delete; Candidate A's "one hold" (body replacement only); §10.2 citations; §9 search.
   **Scenario:** A note already in the vault contains hidden instructions (AgentFlayer's shape; MINJA's outcome). The assistant reads it, which taints the turn. Candidate A blocks replacing some other note's body. The same turn appends a paragraph to the owner's decision note, removes the tag that kept that note out of a query, changes `type` so structured query starts returning it, or soft-deletes the note that contradicted the instruction. Soft-delete also writes a suppression, so the note leaves search and a later ingest will not bring it back. The next answer cites the damaged note at the new revision. The badge, if it has faded, does not travel with the citation. The hold on full-body replacement does not cover any of those mutations. A write key does not even need a tainted turn: ING-12 today, and Candidate A, let any write credential propose or apply those mutations against any document.
   **Recommendation:** Authorize by capability, not by "has the write scope." Hold, as proposals, every mutation outside the capability. Inside a tainted turn, also hold body replacement, append, type change, property change, tag removal, and soft-delete when the target was not created by this actor. Creates and appends to the actor's own documents in the lane still apply, flagged `derived`.

3. **Major — A standing grant must be authored in settings, bound to an operation and a path, and must not be mintable from a card or a tool argument.**
   **Concerned:** SEC-10; SEC-12; the `write` scope (§15.4); Candidate A (no capability, only rate limits and a freeze); Candidate B (capabilities, stated correctly, lifecycle separate); Tana's `autoApprove` argument; Muse and Grok Bot "Always allow"; OpenClaw reusable-approval title in the notes.
   **Scenario:** The owner clicks Approve on one transcript fix and the UI offers "always allow this." The next call's arguments differ: a different path, a delete, a larger body. The client stored a rule. Tana's documented `autoApprove: true` shows the same shape on the server if the model is allowed to set it. Candidate A's rate limit slows the rewrite and does not define which documents the key may touch. A nightly script and a stolen key have the same scope.
   **Recommendation:** Capabilities are rows the session writes, with step-up, naming credential, operation, path prefix, and whether the grant is limited to documents that credential created. The model has no tool that inserts a row. Approving one proposal does not insert a row. "Always" in the UI is a link to the settings form, pre-filled, not a commit. A grant binds the operation class and the prefix. It does not bind a free-form argument pattern the model can widen. Revoking or narrowing the credential bumps its generation (SEC-9) and drops the grant in the same transaction.

4. **Major — Auto-confirm, and a badge that expires into an ordinary citation, are silent acceptance.**
   **Concerned:** Candidate B's confirm-after-a-window; Candidate A's marker that fades after N days; CHAT-1; §10.2 citation resolution (`deleted` and `changed` only); Supermemory's explicit non-expiring inference flag.
   **Scenario:** A derived note is wrong. The owner is away longer than the window. The revision flips to confirmed, or the chip stops saying an agent wrote it. A later answer cites it as the owner's knowledge. Mem0's audit and Graphiti's invalidations are what a store looks like when that flip is the default. Copilot Memory's 28-day deletion runs the other way and still refreshes on use, so cited junk persists.
   **Recommendation:** `review_state` is `confirmed` or `unreviewed` for the life of the revision. A session may mark a revision or a credential-day as seen; that sets `confirmed` and changes no bytes. No job sets `confirmed` because time passed. The UI may stop painting a chip after `writes.marker_fade_days` (default 7). Search responses, citation records, and `brain_get` still return the state. Assistant retrieval down-ranks `derived` unreviewed revisions and never treats reading them as a clean turn.

5. **Major — Mass revert is undefined where human edits, natural-key upserts, and suppression meet.**
   **Concerned:** §5.3 revisions and natural keys; ING-2; ING-9; ING-12 natural-key row; §8 journal and conflict-preserving writes; FLD-6; CAL-4; D13; Candidate A's "revert everything this credential did since <time>."
   **Scenario:** The agent replaces a note at revision 4. The owner edits revision 5 in the editor. Mass revert writes revision 4's predecessor over revision 5 and destroys the owner's paragraph. Separately, a script the owner granted `transcripts/` re-imports an `.ics` container it created and updates a member. The owner reverts that member. The next night's import has the same bytes, ING-2 treats them as the container's current truth, and the reverted body returns. A folder reconcile of an index-mode file does the same if the file on disk still holds the agent's bytes. A soft-delete's suppression stays set after a naive file restore, so the document comes back and stays unindexed, or the suppression is lifted and a watcher immediately re-admits the poisoned file.
   **Recommendation:** Specify revert as a forward journaled mutation, per document, in one state transaction. Apply it only when every revision after the chosen pre-image was authored by the credential being reverted. Otherwise return `interleaved` and do not write. For a reverted container member, record a content pin: reconciliation may not re-apply that content hash until the source bytes change. Revert of a soft-delete is restore plus clearing the suppression this delete created, and only if trash still holds the file. Purge remains irreversible here. Folder and calendar automatic reconciliation are not agent writes and are not in the mass-revert set; reverting one of their revisions is a separate session action with the same pin.

6. **Major — Review state is not in the revision, the publication snapshot, or the citation, so revert and rebuild lie.**
   **Concerned:** §5.2 Revision; §5.1 publication; §8 coordinator; A.1 `revisions`, `indexed_documents` (A.2), citations in §10.2; SEC-25 lineage; U10 rebuild.
   **Scenario:** An agent write publishes. The index snapshot has no `review_state`, so a search hit cannot mark it without joining live state, which the spec forbids for search. A citation stores revision and excerpt. The owner reverts. The citation resolver knows `deleted` and `changed`. `changed` opens whatever now sits at the locator if the implementation treats "revision moved" loosely, or it opens the reverted bytes under a chip that still looks like the agent's claim. Rebuild rebuilds projections from vault plus state. If the marker lived only in a feed table that rebuild does not define, U10 drops it. A proposal payload expiry (SEC-25) is a separate clock from the revision; reverting must not depend on the proposal payload still existing.
   **Recommendation:** Put author credential, `review_state`, `derived`, and `reverts_revision` on `revisions`, copy them into the index metadata snapshot, and copy them into the citation at cite time. Add resolution `reverted`. On `reverted` or on excerpt-hash mismatch, show the stored excerpt and do not retarget the passage. The journal records `direct_write` and `revert` with the same prepare, apply, finalize rules as a proposal. The pre-image for revert is the previous revision's content hash, which the vault or the revision history must still hold; do not require the proposal payload.

7. **Major — The MCP contract will either double-gate honest writes or launder them through `readOnlyHint`.**
   **Concerned:** §7.4 `brain_remember` and `brain_update`; Appendix D annotations; MCP 2026-07-28 tools SHOULD and annotation rules; Hermes `trust: untrusted` as documented in the notes.
   **Scenario:** `brain_update` is specified to always create a proposal. After the policy change it sometimes applies. A client that only shows a pending card waits forever. A client such as Hermes with `trust: untrusted` prompts on any tool whose `readOnlyHint` is false, so the owner approves in Hermes and the server applies, which is two prompts for the common case, or the owner sets the server trusted and the server is then the only gate. If an implementer sets `readOnlyHint: true` on `brain_remember` to silence Hermes, a careless client skips its SHOULD and a stolen session of that client writes without the prompt the user thought the trust setting provided. The server would still enforce lanes. The annotation would still be false.
   **Recommendation:** `brain_remember`, `brain_update`, and any delete tool return a discriminated result: `applied` with document id, revision, `review_state`, and `derived`, or `pending` with `pending_id`. Annotations stay honest: `readOnlyHint: false` on every writing tool; `destructiveHint: true` on replace, tag removal, type change, and delete; `destructiveHint: false` on create and append; `idempotentHint: false`; `openWorldHint: false`. Document that a client prompt is the client's SHOULD and is not a SecondBrain control. Do not add a server flag that advertises writes as read-only. `brain_update` applies when the lane and the taint rule allow, and returns a proposal otherwise. It never takes an `autoApprove` argument.

8. **Major — Revocation, freeze, and a prepared journal row do not yet have one generation check across the new write paths.**
   **Concerned:** SEC-9; §8 journal ("Apply and finalize recheck both revision and generation"); CHAT-13; Candidate A's freeze switch; the OpenClaw titles in the notes.
   **Scenario:** A key is revoked after prepare and before finalize. The current journal text rechecks generation for the proposal path. A new direct-write path that copies only the happy prepare/apply/finalize and forgets the generation recheck commits the revoked key's bytes. A freeze that only rejects new HTTP calls leaves a leased ingest job, admitted under the daemon's identity for a folder, untouched — correct — and leaves a direct write's prepared row able to finish — not correct. A mass revert starts, the key is un-frozen by a race, and new writes land in the middle of the revert set. Separately, a capability row survives a scope narrowing because it is not updated in the SEC-9 generation transaction.
   **Recommendation:** Every direct write, revert, and proposal execution carries the credential id and generation captured at prepare, and apply/finalize fail the row if the generation or the account epoch is stale. Freeze is a credential flag checked in that same transaction; while set, prepare fails. Mass revert takes the per-document publication locks in a documented order and refuses documents that change revision between selection and apply (`interleaved`). Narrowing scopes or revoking a capability is the same transaction as the generation bump. Folder and calendar jobs stay on the daemon identity and are not frozen by a key freeze. In-flight assistant turns still end `partial` / `revoked` at the next tool boundary (CHAT-13).

9. **Minor — An activity feed that includes source reconciliation will train the owner to ignore it.**
   **Concerned:** ING-12 registered-folder column; CAL-4; enrichment write-back; Candidate A's "grouped by credential and day."
   **Scenario:** A calendar subscription refreshes daily and a watched notes folder autosaves. Hundreds of `source` revisions bury the one derived note. The owner stops opening the feed. The derived note is never reverted.
   **Recommendation:** The feed defaults to credential kinds `api_key` and the assistant principal, `review_state = unreviewed`, with `derived` sorted first. Source reconciliation, enrichment, and session-editor revisions are available on a filter and are `confirmed` or `source`, not `unreviewed`. One row per document per credential per day, expandable to revisions.

10. **Minor — Candidate B's provisional revision is a second publication protocol the journal does not need.**
    **Concerned:** §8 coordinator; D17; A.1 `pending_operations` and `mutations`; Candidate B.
    **Scenario:** A provisional revision is visible to search, so it is published. Auto-confirm then either mutates the same revision in place (citations change meaning without a revision bump) or writes a new revision with identical bytes (jobs, idempotency, and the fence all move for no content change). A reader who pinned the provisional revision now has a `changed` citation whose excerpt still matches. Crash recovery has two states to finalize for one file write.
    **Recommendation:** Do not add a provisional revision state. The applied file is the revision. `review_state` and `derived` are columns. Confirm and fade do not go through the journal. Proposals remain the only unpublished writes, and only for the hold and for out-of-lane mutations.

## Recommended design

Name: **granted lanes**. Default `writes.review: after`. `before` restores today's proposal gate for keys and for the assistant, and does not relax hard gates. Session editing stays direct in both modes.

### Replacement for D10

Writes follow one matrix. A write credential applies a mutation immediately only when a session-authored capability covers that operation and path, and the taint rule does not hold it. Applied key and assistant writes are normal revisions with `review_state = unreviewed`. Interactive editing is `confirmed`. Registered sources reconcile automatically and are not agent writes. Proposals remain for everything else. Only a browser session or a paired CLI session approves, reverts, or grants a capability. Keys never approve, never grant, and never revert. The clock never confirms a revision.

### Mutation-policy matrix (replaces the ING-12 table)

`direct` publishes a revision through the journal and the coordinator. `proposal` stores one immutable payload and does not publish. `automatic` is the registered source, unchanged in authority. `denied` is a 403 with a stable problem type.

| Operation | Browser or paired CLI, editing | Assistant turn, `writes.review: after` | Write key inside a capability, `after` | Write key outside every capability, or `writes.review: before` | Registered folder or calendar subscription |
|---|---|---|---|---|---|
| Create | direct, confirmed | direct in the assistant lane; `derived` if the turn is tainted; unreviewed | direct, unreviewed, path must match the grant | proposal | automatic, cause `source`, confirmed, omitted from the default feed |
| Append | direct, confirmed | direct if the target was created by the assistant; if the turn is clean, also direct inside the lane; if the turn is tainted and the target is not the assistant's, proposal | direct, unreviewed, if the grant covers the path or `own_only` matches | proposal | automatic for that file's own bytes |
| Replace body | direct, confirmed | proposal when the turn is tainted and the assistant did not create the target; otherwise direct inside the lane | direct, unreviewed, only if the grant includes `replace_body` for that prefix or own document | proposal | automatic for that file |
| Change type or properties; remove a tag | direct, confirmed | same rule as replace body | direct only if the grant names that operation | proposal | automatic from frontmatter; overrides win |
| Add a tag or a link | direct, confirmed | direct inside the lane, including tainted turns; proposal outside the lane | direct if the grant includes `tag_add` or `link_add` | proposal | automatic |
| Soft-delete (suppress and trash) | direct, confirmed | proposal unless the assistant created the target and the grant includes `soft_delete` | direct only if the grant includes `soft_delete` | proposal | not a suppression; absence only (FLD-6, CAL-4) |
| Restore; lift a suppression | direct, session | denied | denied | denied | not applicable |
| Natural-key upsert | not applicable | denied | direct only for a container this credential created and a grant covering that container; unreviewed; a later revert pins the content hash | proposal | automatic inside the re-imported snapshot |
| Revert one revision; mass revert | direct, session, no step-up; `interleaved` leaves bytes unchanged | denied | denied | denied | not in the agent revert set |
| Freeze a credential | session, step-up | denied | denied | denied | not applicable |
| Approve or discard a proposal | session approves; creator may discard | denied | discard own proposal only | discard own proposal only | not applicable |
| Purge; create, revoke, or narrow credentials; grant or revoke a capability; sources; type registry; `writes.review`; retention | session, step-up; admin keys keep the SEC-10 exception for credential rows and do not gain capability grants or purge | denied | denied | denied | denied |

Taint is decided by the executor from the turn's execution record, never from the model. A turn is tainted if it contains any search hit, read document, neighbor, or compaction summary that records document ids. Reading an unreviewed or derived document taints. A clean turn is one whose record shows none of those. Initial retrieval that returns no documents leaves the turn clean.

The assistant principal is not the browser session. It has its own capability rows, seeded at init to create, append, tag-add, and link-add under `notes/assistant/`, plus `replace_body` and `soft_delete` only on documents it created. The owner widens that in settings with step-up. A new write key is seeded to create, append, tag-add, and link-add under `notes/agents/<credential-name>/`, and `replace_body` / `soft_delete` only on documents that key created. Both seeds are capabilities, so they are visible and revocable. They are not implied by the `write` scope.

`writes.review: before` forces the proposal column for the assistant and for write keys, including inside a grant. It does not turn session edits into proposals.

### Revision state

There is no provisional state.

- A session edit, an approved proposal, a source reconciliation, or an enrichment write-back (when enabled) writes `review_state = confirmed` and `derived = 0`. Cause stays the existing cause (`edit`, `ingest`, `enrichment`, …) plus `revert`.
- A key or assistant apply writes `review_state = unreviewed`. `derived = 1` only when the writing turn was tainted. A key that is not in a turn has `derived = 0`.
- A session marks seen: set `review_state = confirmed` on the named revisions. No new revision, no journal file write, no publication of new bytes. The index snapshot's copy of `review_state` updates through the coordinator as a metadata-only publish that does not bump the content revision. Jobs fenced on content revision stay valid. Citations keep the `review_state` they stored at cite time.
- Revert writes a new revision, cause `revert`, `review_state = confirmed`, `reverts_revision` set, content hash equal to the pre-image. The reverted revision stays in history.

### Mass revert and the content pin

Input: credential id, inclusive start time, optional end time. Select revisions in that window authored by that credential, excluding cause `source`, `enrichment`, and `revert`. Group by document. For each document, under its publication lock:

- Let R be the latest selected revision and P the content hash of the revision immediately before the earliest selected one, or "absent" if the document was created in the window.
- If any revision newer than the earliest selected revision was authored by anyone else, return `interleaved` for that document and do not write.
- Otherwise journal one revert to P, or a soft-delete undo if the net effect of the window was a delete and trash still holds the file. Clearing suppression clears only suppressions whose reason is `user_delete` or `revert_pin` and whose creating credential is the one being reverted.
- If the document is a container member and the reverted hash was applied by natural-key upsert, insert a suppression-like pin `(container, member_key, content_hash)` with reason `revert_pin`. ING-2 and CAL-4 must not apply a member body whose hash equals a live pin. A changed source hash clears the pin and admits the new bytes. The pin is not a user suppression and does not hide the document.

Freeze, checked in the prepare transaction, rejects new prepares from that credential while set. The owner may freeze and mass-revert as two calls. Mass revert does not imply freeze.

### Rate limits

Add to `limits.per_credential`, enforced before commit, `429` with nothing queued, same as today's limits: `writes_per_hour` 30, `creates_per_day` 100, `write_bytes_per_day` 5 MiB. A derived-write breaker: more than 50 `derived = 1` revisions from one credential in 24 hours, and further derived applies from that credential become proposals until a session marks the backlog seen or raises the cap. Ordinary creates inside the lane keep applying. This is the Mem0 junk brake, not a review queue for the nightly script.

### Data model (Appendix A)

`credential_capabilities`: `id`, `credential_id`, `op` (`create`, `append`, `replace_body`, `change_type`, `change_props`, `tag_add`, `tag_remove`, `link_add`, `soft_delete`), `path_prefix` (vault-relative; no `..`), `own_only`, `granted_by` (session id), `created_at`, `revoked_at`. Unique on `(credential_id, op, path_prefix, own_only)` where `revoked_at` is null.

`credentials`: add `frozen_at`.

`revisions`: add `author_credential_id`, `review_state`, `derived`, `reverts_revision`, `turn_id` nullable. `cause` gains `revert` and `direct_write`.

`documents`: add `created_by_credential_id`. Denormalize nothing else; the current revision row is the source for the snapshot.

`content_pins`: `id`, `container_document_id`, `member_key`, `content_hash`, `credential_id`, `created_at`, `cleared_at`.

`mutations.kind` gains `direct_write` and `revert`.

`pending_operations` stays. Status set unchanged. It is no longer the path for in-lane applies. `approved_by` remains a session.

`indexed_documents` gains `author_credential_id`, `review_state`, `derived`. Rebuild copies them from state.

Citation object gains `review_state` and `derived`, stored with the citation. Resolver states: `current`, `changed`, `deleted`, `reverted`.

### REST, MCP, CLI, UI

REST:

- `PATCH` and `DELETE` from a key return `200` with the new revision when the matrix says direct, and `202 {pending_id}` when it says proposal. The body includes `review_state` and `derived`. Stale `If-Match` stays `412`.
- `POST /documents/{id}/revert` and `POST /credentials/{id}/revert` are session-only. Response lists `{reverted, interleaved, pinned}` per document.
- `POST /credentials/{id}/freeze` and `DELETE` of that freeze are session plus step-up.
- `GET/POST/DELETE /capabilities` are session plus step-up. No MCP tool.
- `POST /revisions/{document_id}/{revision}/seen` and `POST /activity/seen` are session, no step-up.
- Search hits and `GET /documents/{id}` include `review_state`, `derived`, and `author` provenance.
- `GET /activity` defaults as in finding 9.

MCP: result shape and annotations as in finding 7. `brain_update` description says it applies when the credential's grant covers the edit and otherwise returns a proposal the user approves in the browser. No approve tool.

CLI: `brain login` keys stay unable to approve. `brain activity`, `brain revert`, `brain freeze` require a paired session. `brain add` from a key follows the lane.

UI: the Approvals screen becomes Activity, with a pending-proposal section on top, then derived unreviewed, then other unreviewed. One-click revert on a row. ### M2 exit criteria that replace the approval bullets

- A default write key creates under `notes/agents/<name>/` and the document is keyword-searchable within the ING-4 deadline, with `review_state = unreviewed`.
- The same key's body replace of a document outside the lane returns `202` and does not change bytes.
- A tainted assistant turn that replaces or appends to a document it did not create returns a proposal. A tainted turn that creates inside `notes/assistant/` returns a revision with `derived = 1`.
- Search and citation payloads include `review_state` and `derived`. A reverted citation resolves to `reverted` and serves the stored excerpt.
- Mass revert restores the pre-image when the credential still owns the tip, returns `interleaved` when a session revision is newer, and a second import of the same member bytes does not undo a pin.
- Revoke and freeze between prepare and finalize do not publish. Two concurrent applies of one document publish one revision.
- No writing tool is listed with `readOnlyHint: true`. No test or job sets `review_state = confirmed` because a timestamp elapsed.
- The existing exactly-once crash test still holds for `direct_write` and `revert`, not only for proposals.

## Open decisions for the owner

1. **Default lane for a new write key.** Recommend `notes/agents/<credential-name>/` plus own-document edit and soft-delete. Reason: Claude Code can save immediately, and it cannot rewrite the vault until you add a prefix in settings.
2. **Default lane for the assistant.** Recommend `notes/assistant/` with the same own-document rule. Reason: U8 becomes a direct save; a tainted rewrite of your notes stays a proposal.
3. **Whether tainted creates inside the lane apply.** Recommend yes, flagged `derived`, down-ranked for the assistant. Reason: holding them recreates the queue; hiding them makes the save invisible.
4. **Whether a tainted append to the assistant's own note applies.** Recommend yes. Reason: the note is already agent-authored and unreviewed.
5. **Display fade.** Recommend 7 days, display only. Reason: long enough to see a bad week; the citation data does not expire.
6. **Rate limits.** Recommend 30 writes per hour, 100 creates per day, 5 MiB per day, and proposals after 50 derived revisions per day. Reason: a nightly transcript batch fits; a poisoning loop does not.
7. **Ship `writes.review: before` in M2.** Recommend yes, default `after`. Reason: the old gate stays one switch away while the new path settles.
8. **Step-up on mass revert.** Recommend no, provided interleaved documents are skipped and listed. Recommend step-up on freeze. Reason: revert of an agent tip is the undo you will actually use; freeze disables a live client.
9. **Trash retention.** Recommend keep 30 days. Reason: Tana still needed restore after it had proposals; purge stays the hard gate.
10. **"Mark this credential's day as seen."** Recommend yes, metadata only. Reason: review of a day's agent notes should be one action and must not rewrite files.
