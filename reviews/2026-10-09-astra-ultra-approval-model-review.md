# Approval-model review — GPT-6 Astra, reasoning ultra — 2026-10-09

## Overall assessment

**Change the default for ordinary agent work, but do not adopt either candidate unchanged.** The current proposal model protects existing documents at the cost of making a knowledge-writing daemon awkward for its principal users: agents and unattended scripts. Candidate A removes that friction by granting every write credential authority over almost the whole corpus. Its recovery features are valuable, but recovery cannot prevent an incorrect revision being retrieved, acted on, or copied before anyone notices. Candidate B supplies the better authorization mechanism—human-authored standing capabilities—but its blanket retrieved-content hold preserves much of the built-in assistant's present friction, and automatic confirmation confuses elapsed time with review.

I recommend **scoped automatic writes, durable revision history, and review after publication**. A credential or the built-in assistant may immediately create and maintain knowledge inside explicitly granted ownership/namespace boundaries. Outside those boundaries, it submits an immutable proposal. A normal agent setup grants an agent its own working area once; a transcript pipeline receives its own namespace once. The built-in assistant receives a separate, similarly bounded grant. Human review is exceptional for routine work, required for expansion of authority and protected changes, and available after every automatic change. Unreviewed content remains visibly unreviewed; a timer may quiet the activity feed but may never certify it.

This deliberately changes D10's promise. The enforceable guarantee becomes **an agent cannot mutate outside its standing grant or change the grant itself**. It is not a guarantee that an authorized agent never writes false or injected material inside that grant. SEC-14 should remain unchanged in substance: model resistance, labels, anomaly detection, and another reviewing model are mitigations, never authorization boundaries. `local_only` continues to constrain daemon transport; it does not prevent local misinformation or control an external MCP client's use of returned data.

The previous review's new finding #1 and round-1 disposition #31 were correct about inconsistent enforcement of the then-selected policy. They do not require retaining that policy forever. Their lasting requirement is that REST, MCP, assistant tools, source reconciliation, and implicit upserts use one policy with no alternate-door bypass.

**Scope and evidence.** I read the working-tree README, the relevant contracts and appendices of Draft v0.6, the M2 planning draft, the round-two review, and the supplied reports/notes, and verified the principal external comparisons using live primary sources. Context7 was used for MCP, Claude Code, Gemini CLI, and Hermes documentation. External evidence is dated below; documentation without a publication date is identified by access date, **2026-10-09**. Product documentation demonstrates documented behavior, not an independently audited implementation. Issue reports demonstrate reported failures, not prevalence. M0 is committed; M1 is unfinished working-tree work; M2 remains planning. This is a design review, not an implementation or test certification. No build or tests were run.

### Always-on agents, MCP, and corrections to the supplied evidence

**Hermes.** Current documentation confirms `write_approval` is off by default, but background replace/remove review is still staged even with that setting off. Staged changes bind the target entry and reject a changed target. Approval can occur through CLI or supported messaging surfaces; it is not universally browser-only. Notifications and inspectable pending changes supply part of its lower-friction experience. Its MCP `trust: untrusted` requires approval for tools without `readOnlyHint: true`; unattended calls fail closed when no approver is available. Default trust is documented as `full`. A correctly automatic SecondBrain operation can therefore still be blocked by client policy. [Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory), [MCP reference](https://hermes-agent.nousresearch.com/docs/reference/mcp-config-reference), [plugin implementation guidance](https://github.com/nousresearch/hermes-agent/blob/main/website/docs/developer-guide/plugins/index.md), accessed 2026-10-09.

**Grok Bot, Muse and Dots.** Grok's official approval page, updated 2026-10-06, documents unattended requests expiring after roughly ten minutes without execution; this is request freshness, not a ten-minute standing-grant lifetime or a provisional-content confirmation timer. [Grok documentation](https://docs.x.ai/grok-bot/approvals-security-and-privacy) Meta's 2026-09-08 technical account places Sentinel outside the agent runtime, with grants scoped by connector, destination and use case and an out-of-conversation approval surface. This supports executor-owned authority; the architecture statement is not an independent audit. [Meta technical account](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse) OpenAI's 2026-09-29 account similarly separates Dots' action checks from the writable workspace, permits prior authorization where applicable, retains mandatory sensitive-action checks, and lets background research save private notes. Disconnecting a connection stops future access, not already learned context. [OpenAI technical/product account](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/)

The combined claim that **every** surveyed agent exempts **all** memory writes and converges on the same “Always allow” mechanism is too strong. These systems distinguish actions, private memory, inferred instructions, explicit requests, trust settings and unattended modes in different ways. Their recurring useful pattern is delegated scope plus independent enforcement and observability, not one universal approval policy.

**MCP.** The live 2026-07-28 tools specification contains client **SHOULD** guidance for human confirmation and server **MUST** requirements for access control, validation and rate limiting. The overview also states consent principles; it would be inaccurate to summarize the whole protocol as having no consent requirements. It supplies no evidence that every write must produce a new interactive prompt. Tool annotations are hints, untrusted unless obtained from a trusted server; they are not server authorization. `destructiveHint=false` describes additive updates, not every reversible update. [Tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema), [overview](https://modelcontextprotocol.io/specification/2026-07-28), accessed 2026-10-09.

### What undo research supports

Stewen and Kleppmann's *Undo and Redo Support for Replicated Registers* (submitted 2024-04-17; PaPoC 2024) treats undo in collaborative systems as a problem requiring explicit semantics; it is not simply restoring an earlier snapshot. SecondBrain need not implement a collaborative CRDT, but its human/agent interleaving has the same need to distinguish one's own changes from another writer's later work. The conservative M2 solution is to automate reversal of an uncontested suffix and report conflicts elsewhere. This is an engineering inference, not a claim that the paper proves that specific implementation. [Primary paper](https://arxiv.org/abs/2404.11308)

Git's compensating commits likewise preserve the fact that an earlier change happened. None of these mechanisms can undo information already disclosed, a downstream agent's action, or a belief copied into another memory store. Undo is therefore a recovery control whose value depends on detection time, retained preimages, conflict semantics, and coverage of derived copies.

Microsoft's compensating-transaction guidance explicitly warns that restoring an original state can overwrite concurrent work and that compensation requires durable, application-specific, retryable steps. This is a direct fit for a resumable per-document revert plan. Persistent undo controls also have a usability rationale; a toast that disappears is insufficient for discovering yesterday's damage. [Microsoft architecture guidance, updated 2026-04-20](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction), [Nielsen Norman Group, 2020-11-29](https://www.nngroup.com/articles/user-control-and-freedom/).

## Findings

The findings concern specified guarantees and proposed replacements. Severity denotes the consequence if the relevant design is shipped as described, not a claim of an exploited vulnerability in the unfinished implementation.

1. **Major — The existing gate obstructs the main unattended workflows.**  
   **Concerned:** D10; ING-12; CHAT-3, CHAT-6; §10.2; §21 “Proposal friction for scripts”; M2 goal and work item 4.  
   **Scenario:** A nightly pipeline corrects a transcript property or an MCP agent appends a decision to an existing note. Both wait for a browser approval. A paired CLI session is short-lived human authority, not a satisfactory credential for a nightly job. Moreover, `/chat` declares retrieval inherent to a turn, making the no-retrieved-content auto-approve exception unusually narrow. Creates are already direct for keys, so the current model is not a universal memory-poisoning prevention gate.  
   **Recommendation:** Replace routine approval with human-authored standing grants for specific operations and targets. Keep proposals for operations beyond the grant. Measure unattended completion across the owner's actual four writer classes, not merely whether approval buttons work.

2. **Critical — Candidate A removes the corpus-integrity boundary while retaining a safety claim based on undo.**  
   **Concerned:** Candidate A; D10; CHAT-4; SEC-12, SEC-14; §15.1; §21 prompt-injection risk.  
   **Scenario:** A compromised write key replaces facts across human notes, changes dates/participants to alter structured answers, or plants a new note containing durable instructions. The proposed lone hold does not stop append attacks, property corruption, malicious creates, or an external client whose retrieved context the server cannot observe. Search uses the new content before review; another agent copies it. A later revert repairs the vault but cannot recall that use.  
   **Recommendation:** Do not make `write` mean unrestricted rewrite. Enforce target/operation grants outside the model, protect instruction/configuration inputs separately, and explicitly accept residual misinformation risk within a grant. Labels, time windows, rate limits, and reversibility supplement this boundary; they do not replace it.

3. **Major — Candidate B's taint rule is both too broad for the assistant and unavailable for external writers.**  
   **Concerned:** Candidate B; CHAT-6; §10.2 context assembly and compaction; §7.4.  
   **Scenario:** The built-in assistant reads a transcript and cannot save its requested summary without approval, while Hermes performs the same read outside the daemon's conversation and submits an automatically authorized write. Reusing conversation history may keep every later built-in turn tainted. A client-supplied `retrieved_content: false` would be an assertion, not proof.  
   **Recommendation:** Make server-enforced capability checks the common rule. Persist built-in exposure from actual execution/history, and mark external context as unknown. Permit derived writes inside a deliberately granted agent area; require proposals outside it. Never clear provenance because a new turn, compaction, or timeout occurred. Explain that this is a deliberate modification to B.

4. **Critical — Standing grants can be bypassed if assistant calls inherit session authority or admin keys can mint stronger writers.**  
   **Concerned:** Candidate B; SEC-8–12; §15.4; §7.3 `/keys`; §10.2 optional profile note.  
   **Scenario:** A browser session holds all scopes and approval rights. If a model tool invocation uses those editor privileges, it bypasses its own limited grant. Separately, current SEC-10 explicitly allows an admin API key to manage credentials without session step-up. Letting that route issue broad grants would defeat “human-authored capabilities.” An automatically mutable profile note could also become privileged prompt context.  
   **Recommendation:** Record server-set actor kind and a separate built-in-assistant policy subject. Require an interactive, stepped-up owner session for issuing or broadening standing grants and activating instruction/configuration revisions. Do not accept a tool argument claiming direct-human origin. Remove or explicitly constrain the admin-key credential-issuance route; this is a change to M0 behavior, not merely new M2 UI.

5. **Major — Retained revision numbers do not provide reversible content or per-revision attribution.**  
   **Concerned:** ING-3; §§5.1–5.3; Appendix A `documents`, `revisions`, `payloads`, `mutations`; both candidates.  
   **Scenario:** The owner attempts to undo yesterday's rewrite. `revisions` contains its hash and cause, but no old body, complete authored metadata, or stable writer identity. A document-level provenance string cannot establish which credential changed revision 12 or whether a renamed credential created the document. The disposable index cannot supply authoritative history.  
   **Recommendation:** Persist immutable pre/post authored snapshots and writer IDs before accepting recoverable writes; preserve credential-name snapshots for display. Retain original/effective properties, overrides, tag assertions, links, lifecycle/occurrence data, and lineage, not just text. Define storage reservation and history retention before promising undo.

6. **Major — “Revert everything this credential did” can erase intervening human work.**  
   **Concerned:** Candidate A's mass revert; Candidate B's revert; §§5.3, 8; Appendix A revisions/journal.  
   **Scenario:** Human revision 10 is followed by agent 11, human 12, and agent 13. Restoring revision 10 removes revision 12. Reverting only 13 leaves the effect of 11. Even a textually clean inverse can invalidate a later fact that depends on the removed text. An agent-created document may now contain substantial human authorship.  
   **Recommendation:** Freeze and materialize the operation selection at a stable sequence cutoff. In M2, automatically reverse only selected contiguous suffixes, using a new compensating revision. Report interleaving as a conflict; never silently reset the head or ask a model to resolve it autonomously. Offer explicit conflict resolution and a separate quarantine action for suspected poisoning.

7. **Major — Automatic confirmation and fading markers would launder unreviewed text into apparently authoritative knowledge.**  
   **Concerned:** Candidate A's fading marker; Candidate B's auto-confirm; CHAT-1; RET-7; §10.2 citations.  
   **Scenario:** A false property is immediately cited from a provisional revision. Seven days later the owner still has not looked, but the marker disappears or the revision becomes “confirmed.” A later citation reader interprets it as owner-reviewed. Human revision 12 also inherits unreviewed content from agent revision 11 even if the human only fixed a typo.  
   **Recommendation:** Separate publication, authorship, review, and retraction. Time may move an activity item out of the active feed; it must not set `reviewed_by`. Carry server-authored provenance and review status in search, resources, tool results, and citations. Review is revision-specific; editing a small part does not review the whole document.

8. **Major — Revocation needs a defined mutation cutoff, not only tool-call checks.**  
   **Concerned:** SEC-9; CHAT-13; §15.4 admitted ingestion; §8 journal; candidate freeze switches.  
   **Scenario:** A key is frozen after an edit was prepared but before filesystem apply. A worker or crash recovery uses cached capabilities and applies it anyway. Conversely, abandoning an already-applied mutation after revocation leaves a file effect without its revision/audit record. Retaining a captured policy object after a grant is removed recreates a documented class of agent-tool bugs.  
   **Recommendation:** Revalidate current credential, grant, policy generation and target fences at a defined apply-admission boundary. Stop unadmitted authored effects, but finish recording already-admitted effects. Freeze must drain those effects and return the resulting stable cutoff. Already-committed ingestion projections may finish; later authored writes and enrichment write-back are new effects requiring authority.

9. **Major — Automatic soft deletion followed by timed purge bypasses the intended irreversible-action gate.**  
   **Concerned:** D13; §6 trash; ING-12; §15.9 retention; both candidates' purge promises.  
   **Scenario:** A key soft-deletes useful notes and is never reviewed. The existing 30-day retention job purges them without a new human decision, making that key indirectly capable of permanent deletion. Restore may also lift an unrelated suppression that the owner added later. Current `/suppressions/{id}` is write-scoped despite ING-12's interactive-only lift, and source removal with `?purge=1` needs the same purge rule as document deletion.  
   **Recommendation:** Agent-origin trash must not auto-purge merely because 30 days elapsed. Require explicit owner consent to purge it or an explicitly authorized retention policy whose irreversibility is disclosed. Preserve suppression ownership and IDs; restoration may remove only the exact suppression being reversed, and may not override newer ones. Make all purge entry points obey one hard gate.

10. **Major — Ownership and natural-key exceptions can widen a narrow grant silently.**  
   **Concerned:** ING-2, ING-9, ING-12; §§5.3–5.4; CAL-4; candidate “documents it created” and path grants.  
   **Scenario:** An agent changes an existing calendar member through a nominal create/re-import call; changes a natural-key property to collide with another item; moves a document into its namespace; or rewrites a document it created before the owner substantially edited it. “Same credential” in a container rule does not protect later human overrides. Path strings and mutable display names cannot define durable ownership.  
   **Recommendation:** Resolve actual target identities and the full delta before policy classification. Use immutable creator subject IDs, boundary-safe namespaces, explicit shared-document grants, and a persistent protected flag after direct human editing. Authorize every affected container member and lifecycle action; preserve human overrides and suppressions. Do not grandfather the natural-key exception as a second write policy.

11. **Major — Revert and quarantine must reach retrieval and known derived copies through the existing consistency machinery.**  
   **Concerned:** §§8–10; SEC-25–26; Appendix A payload lineage; both candidates.  
   **Scenario:** A rejected fact is restored in the Markdown file, but a stale FTS/vector snapshot still returns it. A compaction summary or generated note copied that fact and keeps feeding later answers. An old citation silently resolves to restored text at the same ordinal. Purge removes the live note but misses the newly added history snapshots.  
   **Recommendation:** Apply reversals through the journal and publication coordinator, fence old workers, and enforce quarantine/suppression at read time as well as indexing. Add revision-level dependency edges to the existing document-level purge lineage. Preserve historical citation identity and show retraction; mark known derivatives suspect, invalidate cached contexts, and never claim to recall unknown external copies. Include revision snapshots and revert artifacts in logical purge.

12. **Major — The MCP contract and clients will not infer the new write model correctly.**  
   **Concerned:** §7.4 `brain_update`; §7.3 PATCH and lifecycle outcomes; Appendix D; Hermes/client integration.  
   **Scenario:** A client believes `brain_update` only stages a proposal, but the same call now changes a document immediately. Or the server is automatic while Hermes still requires approval for a write-capable tool. Describing a reversible replacement as read-only/non-destructive to suppress that prompt would misrepresent it. HTTP retries can duplicate appends without a stable request identity.  
   **Recommendation:** Change descriptions and schemas explicitly; return a discriminated applied/proposed/rejected outcome with revision and policy reason. Keep mutation annotations truthful and server authorization independent. Introduce durable mutation idempotency across REST and MCP. Qualify real client behavior rather than promising that server settings disable client prompts.

13. **Major — Automatic writes need durable capacity limits and a usable recovery surface in M2.**  
   **Concerned:** §15.8; §11; §§19–20; Appendix B; M2 acceptance gates.  
   **Scenario:** A permitted agent creates thousands of redundant memories or rewrites a large note repeatedly. Ordinary request limits do not bound history growth, embeddings, or review workload. M2 exposes automatic writes before M3 supplies the activity feed or freeze/revert controls; the proposed safety mechanism is unavailable when first needed.  
   **Recommendation:** Reserve per-actor mutation and retained-byte budgets, expose rejected/deferred outcomes, coalesce the feed, and ship the minimal owner controls with M2. Make historical snapshots, recovery, quarantine, citation state and the no-routine-prompt workflows release gates rather than follow-up work.

14. **Minor — Several supplied comparison summaries overstate their primary evidence.**  
   **Concerned:** The two 2026-10-09 reports and the evidence used to choose defaults.  
   **Scenario:** A reported fraction of invalidated graph facts becomes a measured error rate, an agent's self-review becomes human approval, or different Tana products become one incident. These changes can make either universal approval or universal automation appear better evidenced than it is.  
   **Recommendation:** Preserve the qualifications in this review. Use comparable products as mechanism examples, incident reports as concrete failure evidence, and the owner's workload as the acceptance test. Do not select safety defaults from an unverified competitor aggregate.

## Recommended design

### 1. Policy: human-authored standing grants, automatic execution inside them

Adopt a modified B with A's activity and recovery experience. Do **not** retain B's unconditional retrieved-content proposal rule, A's global grant to every write key, or either candidate's implication that age establishes trust.

Proposed replacement for D10:

> All doors use one mutation policy. Ordinary content mutations execute immediately when the authenticated actor has a current standing grant for the operation and every affected target; otherwise they require an immutable proposal approved by an interactive owner session. Grants are created or broadened only by an interactive owner with step-up. Automatic changes retain attributed snapshots and remain unreviewed until explicitly reviewed. Agent tools cannot grant authority, activate instructions, lift owner protections, or purge. Registered-source reconciliation retains separately registered authority limited to its source.

`write` remains an admission scope, not a universal target grant. Grant evaluation uses structured fields, not natural-language rules interpreted by a model:

- **Subject:** immutable credential ID, or the dedicated `builtin-assistant` subject. The initiating session/key is separately recorded. Credential names are display data.
- **Operations:** `create`, `append`, `replace_body`, `set_title`, `add_tags`, `remove_tags`, `set_properties`, `change_type`, `add_links`, `remove_links`, `soft_delete`, and, where implemented, `reconcile_container`. Each operation is opt-in. A mixed PATCH must satisfy all of them or become one proposal; never partly apply it.
- **Targets:** explicit document IDs or a normalized vault-relative namespace, optionally constrained by immutable creator subject, type and allowed property names. M2 needs literal prefixes on path-component boundaries, not arbitrary expressions. A rename/move must authorize both old and new target sets and cannot change creator identity.
- **Protection:** default grants exclude owner-protected documents, registered sources, external files, instruction/profile inputs and all control-plane resources. A broader shared-content grant can explicitly include protected ordinary documents. It still cannot include the control plane or active instructions.
- **Bounds:** size, rate and daily retained-byte quotas, expiry if chosen, grant version and current enabled/frozen state. No client or model can set these through content/frontmatter/tool arguments.

Normal setup offers **capture and maintain my own area** as the recommended write preset. It grants create/append/body/title/tag/link/property changes to supported managed Markdown under `notes/agents/<immutable-subject-id>/`, restricted to documents created by that subject and not subsequently protected. Changing an existing document's type and soft deletion are absent from this preset; registry changes are never ordinary content authority. A direct human editor save of an agent-created document sets `protected=true`; subsequent own-area writes propose changes until the owner explicitly permits shared editing. Reviewing a revision alone does not protect or transfer the document.

A nightly script instead receives a purpose-specific namespace such as `notes/transcripts/nightly/`, its supported content types, its property fields and ordinary update operations. This makes repeated corrections automatic without granting the gateway access to every personal note. Container reconciliation remains M4 behavior and needs a separately specified grant. Unsupported types stay unavailable until that milestone implements them.

The built-in assistant gets a dedicated grant over `notes/assistant/`. A browser starting a chat does not lend the assistant editor/admin/approval authority. For an API-initiated chat, the effective rights are the intersection of the caller's grant, the assistant grant, and the surface tool set; setup can explicitly give that client access to the assistant area. Outside the effective grant, the model can create a proposal but cannot execute it.

Once these grants exist, summaries made after retrieval apply automatically in the relevant working area. The executor records `context_origin=observed_retrieved`, including inherited context/compaction and profile material; external writes use `external_unknown` unless the daemon itself observed the relevant execution. A client-declared dependency can add lineage but cannot establish an untainted context. These facts prioritize inspection and support incident response; they do not widen authority or gate every ordinary write.

`writes.review: after` is the default **within a standing grant**. `before` forces non-human content writes through proposals even within their grants; it does not grant missing rights or change human editor/source behavior. Per-grant `before` can make one high-value collection more conservative. A global or applicable target-level `before` restriction wins over an overlapping permissive grant; hard denies and protections are evaluated first. Keep the read-only default bridge. For existing installations, migrate old `write` credentials without broadening them: retain capture to a generated assigned area, require the owner to select new update grants, and mark legacy history/ownership as unknown rather than guessing.

Missing `write` denies mutation/proposal creation. Hard-gated actions require `admin`, current interactive authority, and fresh step-up unless the row says otherwise.

The approval card has no “always allow” button. Settings can offer a separate grant workflow, with step-up and a fresh concrete target/operation summary; it must not synthesize a broad rule silently from a successful card.

### 3. Revision and review state machine

Use **one published content head per document**. “Provisional” means **applied, available to retrieval, and not human-reviewed**. It does not mean hidden, sandboxed, or safe. Avoid a second confirmed-head index in M2.

```text
request -> denied / limited / conflict
        -> pending proposal -> expired / discarded / superseded
                            -> approved instance -> journal
        -> admitted standing grant -------------> journal

journal: prepared -> apply_admitted -> applied -> finalized
                    \-> failure/conflict before an effect

finalized authored revision:
  current, unreviewed -> current, reviewed        [explicit review of this revision]
  current            -> historical              [a newer monotonic revision]
  selected bad change -> retracted marker        [with a compensating revision or quarantine]
  any retained bytes -> redacted                 [logical purge]

attention: open -> quiet after 7 days             [no change to review or provenance]
```

Publication/readiness (`publishing`, lexical-ready, vectors pending), document lifecycle (`live`, `deleted`, `purged`), review, and quarantine are separate axes. Do not overload `documents.status` with a single provisional state that loses these distinctions. Review changes have their own sequence/version and do not invent a content revision or trigger embeddings.

Every non-human revision starts unreviewed. A human edit records human authorship of that change; it does not automatically approve all inherited material. A direct human creation can start with `review_origin=user_authored`. An explicit “Review this revision” action marks the exact full snapshot reviewed and does not cover later edits. Historical review events remain attached to their original revision after retraction or purge, with content removed as required.

By default search/query/get return the current, non-suppressed, non-quarantined head, including unreviewed content. Each result includes writer provenance, `review_status`, `review_origin`, context origin, and known retracted-input status. `review=reviewed_only` is an optional filter over current heads; it omits unreviewed heads rather than silently serving an older version. Return exclusion counts/reasons so an empty filtered search is not mistaken for absence of knowledge. Do not conflate this user-selected filter with vector degradation.

No score penalty is required in M2: automatically reducing all agent-written material could make the owner's principal corpus hard to retrieve. A later ranking experiment can use measured relevance. The visible marker and machine-readable status remain regardless of feed age.

### 4. Durable history, publication, and exactly-once execution

Before admitting an authored mutation, stage and validate its normalized payload and complete affected-target set. Under the document reservation/coordinator, retain the observed **preimage** and intended **postimage** as immutable authored snapshots, including raw managed Markdown and canonical authored metadata. Capture properties and overrides separately from derived projections so a revert cannot lose `props_original` or turn a model-enriched field into a human assertion. Store the base schema version. Derived chunks/vectors remain disposable and are rebuilt through the normal pipeline.

For M2, automatic body editing is limited to supported managed Markdown. Non-Markdown original replacement, external-file write-back and containers need their own demonstrated preimage/restore semantics before receiving an automatic replacement grant. Capture of a new supported file remains possible inside a create grant. Metadata operations on supported types can be automatic because their authored state is snapshotted. Observing external source changes must not promise recovery of bytes that disappeared before the daemon saw them.

Extend the journal to every authored mutation, including metadata-only changes and compensation. Metadata-only effects can finalize in one state transaction, but still produce the same operation, revision, attribution, review, lineage and idempotency records. Filesystem operations retain prepare/apply/finalize and conflict-preserving file handling. New history refs must be durable before apply; inability to reserve or persist them rejects the write rather than degrading silently to non-reversible execution.

At **apply admission**, serialize the current authority check with freeze/grant-policy updates; persist the credential generation, account epoch, matched grant/version, exact payload hash, target revisions/live hashes and the admission decision. This is the irreversible-effect cutoff. A revocation prevents new admissions. A permit already admitted can finish, including crash recovery, and must finalize its audit even if authority has since been revoked. Freeze waits for admitted effects to settle and reports their final change sequence; it cannot honestly claim that a previously admitted filesystem write never happened. A process crash during freeze resumes this drain before presenting a completed incident cutoff.

Finalize the revision, change record, execution outcome, grant quota settlement, proposal resolution if any, and replayable idempotency result together. Publish the resulting authored revision through §8's coordinator. Compensations advance revisions and processing fences; never decrement a head to an old number. Preserve lexical/vector readiness reporting. Existing conflict files remain explicit conflicts and may not be admitted as normal agent notes merely because they sit beside a managed file.

### 5. Single-change and mass revert semantics

M2 should promise **safe automatic rollback when there is no competing authored history**, with explicit partial results elsewhere. It should not promise a general semantic selective-undo engine.

1. For incident response, the owner first freezes the credential/assistant subject and optionally quarantines its selected affected heads. Materialize a plan using stable actor ID, server UTC interval, and inclusive final `change_seq` cutoff. Persist the exact selected change IDs, expected current revisions, dependencies and proposed outcomes. Credential/day grouping is presentation; display names and timestamps are not execution selectors.
2. For each document, let the earliest selected unreverted change be `s`. Automatic whole-snapshot compensation is allowed only when every authored revision from `s` through the current head belongs to the selected set. Review events do not count as authored revisions. Require retained preimage, valid target schema, unchanged head/live hash, no later purge, no unrelated suppression, and no namespace/identity collision.
3. Create a new revision restoring the authored snapshot immediately before `s`, attributed to the reverting human and linked to every reversed change. Do not copy its old provenance as the new writer. If the selected suffix starts with document creation, soft-delete the document rather than erase its history. If it reverses deletion, restore only when the exact associated suppression can be removed safely and the destination is free.
4. If any nonselected human, source, or other-agent revision interleaves, return `conflict` for that document. The `H10 -> A11 -> H12 -> A13` example is a conflict for reversing both agent edits. Preserve all bytes, show the diff/preimages, and let an explicit human resolution create a new revision against the current head. A later selective inverse engine can improve convenience; it is not an M2 prerequisite.
5. Process documents with journaled, idempotent compensations; persist batch progress. There is no claim of an atomic transaction across every affected document. A resumed plan reports `reverted`, `already_reverted`, `conflict`, `history_unavailable`, `purged`, or `failed`, never a blanket success for a partial result. Do not continue a stale plan after concurrent edits without recomputing its affected entries.

Quarantine provides containment when a reversal cannot safely resolve interleaved content. It hides affected current heads from normal retrieval/resources/get and from new assistant context without deleting their human additions. A read-only key cannot request quarantined text; the owner can inspect it through the review surface. Known derived revisions are marked suspect and excluded from default assistant context until reviewed or regenerated; normal search can expose metadata explaining withheld results. Unquarantine requires an owner decision. This is an incident action, not a review queue that every normal write must pass.

An ordinary revert changes history going forward; it does not erase historical citation excerpts. A rejected source also does not justify automatically deleting every human document that once cited it. Track dependencies and show the affected artifacts. For external clients, dependency completeness is unknowable: conservatively report `lineage=external_unknown`, and never claim mass revert has repaired another agent's memory or recalled a downloaded result.

### 6. Citation integrity and persistent poisoning

Extend each citation with the stable writer/change identity and review status **at citation time**. On resolution, return current review/retraction/quarantine state as separate metadata. Preserve the existing `(document_id, revision, processing_generation, locator, excerpt_hash)` contract: use the exact retained excerpt when the original location cannot be verified. A restored document with identical text still has a new revision; old citations must not be rebound to it.

A citation to a reverted revision says that the cited revision was later reverted and offers the replacement if there is one. A citation whose source was logically purged returns the redaction marker; it must not reveal history retained for undo. Rendering or replaying an old answer must refresh its source-state overlay rather than pretending its historical review status is current. This adds information to the recorded answer; it does not silently rewrite what the assistant said.

Track known derivation at **revision** granularity. Built-in generated notes, summaries, tool results and compaction already have document lineage; extend those refs to the actual input revision/change where known. Maintain transitive affectedness through those references, with bounded traversal and durable work when a graph is large. On quarantine/retraction, invalidate reusable prompt/compaction caches and replace affected historical material in future model context with a warning/withheld marker, or regenerate it from eligible sources. Check eligibility immediately before each provider call and final delivery; an already-dispatched request or delivered answer cannot be recalled.

An incident advances a durable eligibility generation before dependency traversal starts. For the simple M2 implementation, normal body-bearing retrieval/delivery and new built-in provider calls pause with `incident-check-pending` until that traversal has marked known descendants and invalidated context caches; the owner review surface remains available. Then reads resume against the new generation. Do not claim immediate descendant containment while an asynchronous walker leaves unmarked copies readable. More selective per-artifact eligibility checks can replace the temporary global barrier later.

Logical purge must also reach current managed files generated from known purged inputs, not only their historical payloads. Redact dependency-bearing body/metadata fields through the journal; if lineage is only artifact-level, conservatively redact the whole derived artifact and retain its identity/reason. Apply the same rule to its snapshots and revert artifacts. This is a deliberate extension to D18's known-copy coverage, with the existing named retained classes still explicit. It can redact otherwise useful derived material; it must never claim complete erasure of undeclared external copies.

Do not make ordinary ingested prose active system instructions. The optional profile note must be a separately selected, pinned, owner-approved revision, protected from automatic activation of later edits. Grants, scopes, tool definitions, type schemas, provider destinations and trusted services stay outside model-writeable content. These controls limit what injected prose can cause even when the model follows it. They do not make its factual assertions reliable.

### 8. REST, MCP, CLI and UI contracts

**Shared mutation result.** All surfaces use one normalized operation service and a result union:

```json
{"outcome":"applied","operation_id":"...","change_id":"...",
 "document_id":"...","revision":18,"review_status":"unreviewed",
 "authorization":{"kind":"standing_grant","grant_id":"...","version":3},
 "projections":{"lexical":"ready","vector":"pending"}}
```

Other outcomes are `proposed` with `pending_id` and a stable `reason`, or errors such as `denied`, `revision_mismatch`, `limited`, `history_capacity`, and `conflict`. An asynchronous request returns `accepted` plus an operation/job handle, not a false `applied` result. Proposal IDs and job IDs are different fields. Success text says whether content changed now or awaits action. A write-only caller gets outcome/precondition metadata, never bodies, diffs or another writer's private proposal.

**REST.** Keep existing create/PATCH/delete endpoints and `If-Match`, but replace the key-always-proposes descriptions with the policy matrix. Require `Idempotency-Key` on every mutating API operation, including append, delete, restore, proposal creation/approval, review and revert. Hash the canonical method, target, precondition and payload; a reused key with different intent returns the existing `422 idempotency-key-reuse`. A duplicate authorized retry returns its original effect identity without reserving more quota. Reauthentication remains mandatory; revocation never permits retrieval of old sensitive result bodies merely because an idempotency row exists.

Add these logical routes (all under `/v1`):

| Route | Contract |
|---|---|
| `GET /write-policy` | Effective permitted operations/target summaries and limits for the caller; a read-only key learns only its own configuration, not corpus contents. |
| `GET /operations/{id}` | Bounded status/outcome lookup for the creator or owner, including uncertain transport recovery. |
| `GET /changes`, `/changes/{id}` | Cursor by `change_seq`; filter by actor, date, review and disposition. Owner sees all; `read` keys see only their own activity and only content they can otherwise read. |
| `GET /documents/{id}/revisions/{revision}` and `/diff` | Historical content/metadata, provenance and review state; current read authorization, quarantine and purge checks apply. Unavailable history is an explicit result. |
| `POST /changes/{id}/review` | Interactive only, target revision/hash/review version required; records review, not execution of a new write. |
| `POST /revert-plans`, `GET /revert-plans/{id}`, `POST /revert-plans/{id}/execute` | Interactive; create immutable bounded plan, inspect, then execute the same plan/hash. Ordinary single safe undo can compose planning and execution under current CAS. Larger plans expose scope/conflicts before execution. |
| `POST /writers/{subject}/freeze`, `/quarantine` | Interactive; freeze returns a stable cutoff after admitted work settles; quarantine uses an immutable selected set. Neither is implicit rollback. Unfreeze/unquarantine requires step-up. |
| `GET/POST/PATCH /write-grants` | Inspect per authority; creating or broadening needs interactive step-up and grant-version CAS. Model tools cannot call this surface. |

A stale content target still returns REST `412`; an already-created proposal with changed targets returns `409 target-changed`, optionally with a new immutable suggested proposal. Frozen/revoked subjects cannot create more proposals; pending ones become blocked. The owner may adopt a blocked proposal into a fresh immutable owner proposal after inspecting it. Approval never executes changed arguments, grants a standing capability, or relies solely on authority captured when the proposal was created.

Retain full response payloads for the documented 24-hour replay window, subject to purge. Keep a compact `(subject, request_id, intent_hash, operation_id, disposition)` tombstone for the operation/audit lifetime so a late retry cannot execute again after the response expires. It returns `result-expired` with the operation ID; an intentional new write requires a new request ID. Purge may redact hashes/content that fall under its promise, but must retain a non-content request tombstone sufficient to deny replay as a new effect.

**MCP.** Every mutation tool, explicitly including `brain_remember`, `brain_update` and `brain_delete`, requires a stable caller-generated request ID mapped into the shared idempotency service. `brain_remember` creates inside its grant; `brain_update` accepts a strict operation union for body/title/tags/properties/type/links and an expected revision. Its description must say it may apply immediately under a standing grant or return a proposal. Add a separately named `brain_delete` for explicitly granted soft deletion if exposed in M2, and `brain_operation_status` for outcome verification. An optional `mode: propose` forces review but cannot force execution. Do not expose approve, mark-reviewed, grant, unfreeze or purge as agent tools. REST and MCP use the same field bounds, preconditions and policy reasons.

Keep `brain_update`/`brain_delete` `readOnlyHint=false`, `destructiveHint=true`, and conservatively `idempotentHint=false`; replacement and removal are destructive updates even when recoverable. `brain_remember` is write-capable and additive. Required request IDs provide a precisely documented retry guarantee without overclaiming all semantic repetitions are idempotent. `openWorldHint=false` is appropriate only for tools whose domain is the closed vault; it is not a promise about provider-data egress. `brain_ask` remains read-only. MCP resources and tool text include status/provenance even where a client ignores structured metadata.

The bridge remains read-only until deliberately configured with a named write key and standing grant. Test Claude Code, Claude Desktop compatibility and one Hermes/OpenClaw integration against recorded versions. Explain the independent client approval setting: an owner who wants unattended writes must deliberately permit the selected server/tools in that client, while keeping the daemon grant narrow. Never recommend falsifying annotations to bypass `trust: untrusted`. A client reporting `outcome_uncertain` should query the operation before retrying; server policy cannot make all third-party hosts share one approval UX.

**CLI.** Add `brain changes list|show|review`, `brain undo <change>`, `brain revert plan --writer <id> --since <UTC>`, `brain revert execute <plan>`, `brain writer freeze|unfreeze`, and `brain grants list|show|create|update`. Review/undo/grant commands require paired owner authority where the matrix requires it; nightly mutation commands use ordinary scoped keys. Add `brain update`, `brain delete`, `brain operation get`, and machine-readable mutation outcomes. CLI generates and retains the request ID for a retry. Scripts can request `--require-applied`; if a request becomes a proposal, return exit 4 and its proposal ID instead of reporting successful completion. In ordinary interactive mode show “Applied, unreviewed” or “Proposed, awaiting owner.” No repeating pairing requirement for normal permitted script writes.

**UI.** Rename Approvals to **Activity and exceptions**. Default view groups by writer/day and coalesces repeated edits to a document while retaining expandable exact revisions. Show counts and meaningful net diffs; provide Review, Undo, Freeze, and a separate incident quarantine/revert flow. Prioritize large replacements, deletes, cross-document derivations, repeated rewrites and unknown external lineage without requiring a decision on every item. No daily nag to approve everything. Search/viewer/citations carry a compact persistent unreviewed badge. Settings show actual target boundaries, supported operations, limits, protection rules and the ability to simulate authorization on a document before saving a grant.

The minimum grant, activity, diff, freeze, safe-undo and exception-approval surface ships **with M2**, through the existing browser shell and paired CLI. Full M3 layout/polish can wait. A rollout whose primary writer is an agent needs owner controls on the day automatic writes become available.

### 9. Defaults, retention and hard gates

These numbers are proposed starting values for this single-user product, not research-derived optimal thresholds. Capacity failures must be visible and safely retryable; the owner may tune them in Settings with step-up where increasing authority/capacity matters.

| Setting | Recommended default |
|---|---|
| `writes.review` | `after`, only inside explicit grants; missing authority still proposes or denies. |
| New MCP bridge | Read-only. Selecting the write preset deliberately creates the own-area grant once. |
| Built-in assistant | Own-area create/maintain grant; no delete, shared-document replacement, control-plane or instruction activation authority. Record initial owner selection during setup. |
| Default automatic content | Supported managed Markdown, including structured properties for implemented types; existing identity/provenance/authority fields immutable. |
| Per-subject committed mutations | 120 affected-document mutations/hour and 1,000/day. Metadata, creates, appends, deletes and container-member effects each count; no-ops/idempotent replay do not. |
| Per-subject data volume | 50 MiB/day incoming authored content and 500 MiB/day additional retained snapshot bytes; charge actual storage growth, not just PATCH length. |
| Per-operation automatic text | 1 MiB resulting managed body; larger captures can use an explicitly configured import grant and existing ingestion bounds. Not an excuse to truncate. |
| Batch fan-out | Default 100 affected documents; reserve parsed member count before mutation. M4 container presets may explicitly raise it within ING-7/global bounds. |
| Instance history capacity | Separate 10 GiB default budget and existing free-disk floor; warn at 80%, reject new recoverable writes that cannot reserve their snapshots. Proposal storage also has a bounded count/byte budget; suggest 1,000 open proposals globally. |
| History retention | Pin each change's preimage **and** postimage until 90 days after that change commits, regardless of when the old snapshot was created; keep current content and live proposal/revert-plan pins longer. Derive `revertible_until` from every required snapshot. No indefinite rollback promise. Audit/identity/request tombstones persist; citation excerpts follow conversation retention and purge. |
| Proposal lifetime | Keep 72 hours. Revocation/policy narrowing blocks old proposals; a broadened grant does not automatically execute the backlog. |
| Feed attention | Quiet after 7 days; provenance and unreviewed status persist. No timer-based human confirmation. |
| Trash | 30 days is the minimum ordinary undo period. **Agent-origin trash remains held after that until owner purge consent.** Human-direct deletion can use the owner's explicitly accepted 30-day retention policy. |
| Direct external-file writes / enrichment write-back | Off. Source reconciliation retains its existing limited automatic authority; write-back needs an explicit separate grant. |

Per-subject and global reservations are durable across restart, apply to every door, and prevent a create/re-import request from counting as one cheap operation while replacing thousands of members. Source ingestion can have a separately configured bulk budget, but still consumes global disk/index/history capacity. Capacity exhaustion must not purge unreviewed agent trash or required snapshots early to make room. Offer explicit owner cleanup/export/retention adjustment instead. This is a real availability/storage tradeoff of retaining reversibility.

Hard gates remain for irreversible purge, new or broadened credentials/scopes/grants, removal of owner protection, type-registry definitions/migrations, source authority, privacy/trusted-service/transport changes, retention changes that destroy held recovery data, and activation of prompt/profile instructions. These use current interactive authority and step-up. Narrowing/freezing can be immediate; restoring authority requires step-up. Ordinary content review and uncontested undo need no new password prompt. An approved single protected content edit needs an interactive session, not necessarily fresh step-up, unless it also performs a sensitive action.

Registered automatic retention is itself an advance authorization for irreversible deletion. State this plainly. The default must not quietly translate an agent's soft-delete grant into that authorization. A user may explicitly opt into timed purge of agent trash, but that is an owner risk decision, not part of the recommended preset.

Filesystem custody is part of this boundary. An MCP client with direct write access to the daemon's private vault/state/config can bypass API capabilities. Keep agents on the API or separately registered incoming roots; document that granting them the daemon's OS identity, unrestricted SSH or direct privileged file access changes the threat model. Existing source authority can admit malicious content but must never turn it into grants or configuration.

### 11. M2 exit criteria

Retain existing read-cap, malicious-provider, claim-support, abstention, provider-switch, streaming/replay and privacy gates. M1 closure remains a prerequisite; this review does not establish it. Replace the current blanket “injected instructions cannot cause a filesystem write” requirement with **no out-of-grant or protected-control-plane effect**, plus separate measured model-resistance tests. A model following injected text inside an intentionally broad grant is residual authorized misuse, not evidence that grant enforcement failed.

| Gate | Required evidence before enabling the new default |
|---|---|
| M2-W1: policy parity | A table-driven matrix across REST, MCP, assistant, paired CLI and source paths, including creates, mixed PATCH, metadata, type, delete, restore, suppression, upsert, enrichment and denied control-plane operations. Missing `read` never leaks bodies/diffs. |
| M2-W2: principal separation | A browser-started assistant cannot use the browser's editor/admin/grant/approval rights. Forged actor kind, creator, source, client identity and external `taint=false` cannot widen authority. |
| M2-W3: scope containment | Own-area and explicit shared-namespace updates succeed without prompts; human-protected edits, prefix lookalikes, moves, forbidden property keys, type changes and instruction/profile targets are blocked/proposed correctly. A renamed or rotated key does not acquire ownership. |
| M2-W4: immutable approvals | Concurrent approvals execute once; editing/rebasing/adopting creates a new proposal; revoked creator proposals are blocked; exact targets and payload are checked; an approval never creates a grant. |
| M2-W5: journal and idempotency | Crash injection around snapshot persistence, apply admission, filesystem effect, finalize and publication for ordinary writes and reverts. No lost acknowledged effect or duplicated append; late request-ID replay does not become a new effect after response expiry. |
| M2-W6: freeze/revocation races | Freeze/grant narrowing at each lifecycle boundary produces the specified admitted-or-blocked outcome; recovery records admitted effects; stable cutoff includes all of them; unrelated credentials continue working. Already committed projections may finish without admitting new authored effects. |
| M2-W7: rollback correctness | Safe suffix restores body, original/effective properties, overrides, tags, links and occurrence/lifecycle state. Agent-human-agent interleaving returns conflict and preserves human bytes. Creation with later human authorship is not silently deleted. Revert plans resume with per-item results after crash. |
| M2-W8: deletion and identity | Agent trash survives the 30-day job absent owner consent; explicit purge covers all routes; unrelated/new suppressions are not lifted; purged objects cannot be recreated by revert/upsert. M4 integration must later extend this to actual calendar containers. |
| M2-W9: retrieval and citations | Applied-unreviewed results are immediately usable and labeled; aging never reviews them. Review changes do not re-embed. Reverted/superseded citations keep their original identity and display updated disposition; purge redacts excerpts and history. No stale index or cache bypasses quarantine. |
| M2-W10: lineage incident handling | A poisoned note copied into a built-in generated note and compaction summary is traceable; the eligibility barrier prevents descendant reuse while traversal is pending, including across restart. Future context withholds/rebuilds affected material. Purge redacts current known-derived managed files as well as their snapshots. External unknown lineage explicitly reports incomplete containment. |
| M2-W11: budgets and storage | Repeated large replacement, many small creates, proposal floods, concurrent credentials and batch fan-out cannot exceed reservations. Storage pressure rejects before effects; replay charges once. Rewriting a year-old note preserves its preimage for 90 days after the rewrite. History expiry preserves other live pins/citation refs; purge wins over all pins. |
| M2-W12: recovery portability | Index rebuild preserves authored snapshots, attribution, review and retraction state; the implemented backup/restore mechanism preserves the new authoritative tables/payloads. If full backup remains M4, document and exercise a consistent M2 state/vault recovery fixture without claiming that the unfinished M4 product is shipped. |
| M2-W13: real client contract | Record protocol/SDK/client versions. Exercise stdio and HTTP, a Claude Code round trip, supported Claude Desktop compatibility, and Hermes/OpenClaw trust behavior. A client-side hold and `outcome_uncertain` remain distinguishable from server proposal/denial. No false read-only annotation. |
| M2-W14: owner usability | Minimal browser/paired-CLI grant setup, activity/diff, freeze, quarantine, safe undo and exception approval work at release. A representative recorded workload for Claude Code capture/maintenance, gateway writes, nightly ingestion/correction, and retrieved-context assistant summaries completes **at least 95% of routine in-scope writes with no per-write prompt** after setup. Out-of-scope cases must still hold. Report actual counts; this is a proposed product acceptance target, not an empirical claim. |

M2-W12 does not require prematurely shipping all M4 operations, but it does require proving that the new “reversible” authoritative state survives the same recovery boundary as current data. The owner controls needed to contain automatic changes cannot be deferred as M3 polish. The one-head state model and conservative conflict handling intentionally keep this narrower than a Git-like branching/merge system.

## Open decisions for the owner

These are product/security tradeoffs, not unanswered implementation details. The recommendations above are concrete defaults that can be used to amend the spec immediately.

| Decision | Recommended answer | Reason |
|---|---|---|
| Should ordinary retrieval include automatically written, unreviewed revisions? | **Yes, by default, inside granted work areas; label them permanently and offer a reviewed-only filter.** | Immediate agent knowledge is the purpose of the daemon. Excluding it would relocate the approval bottleneck from writing to usefulness. This explicitly accepts that false material may be used before review. |
| How much authority should a new write integration receive? | **Own-area capture/maintenance preset, selected once; no universal corpus rewrite.** | Makes common writes automatic while containing mistakes and stolen keys. Give the nightly pipeline a distinct namespace. |
| May the built-in assistant save after reading documents? | **Yes, inside its own effective grant.** | Otherwise a normal summary/save workflow remains blocked. Preserve observed dependency provenance and protect shared/curated targets. |
| May an agent continue editing a note after the owner edits it? | **Default no; protect it, with explicit shared-namespace grants available.** | Immutable creation ownership should not grant permanent control over subsequent human authorship. |
| Should time automatically confirm a revision? | **No. Quiet the feed after seven days; leave review status unreviewed.** | No new evidence of review or correctness arises from waiting. |
| Should agents soft-delete automatically? | **Only with a separately selected soft-delete grant; absent from the recommended preset.** | Deletion can remove useful evidence from retrieval immediately even when restorable. Explicitly enabled routine cleanup can still run unattended. |
| May retention permanently delete unreviewed agent trash? | **No by default; require owner purge consent.** | Otherwise a reversible permission becomes an indirect irreversible one. The owner can explicitly choose the storage/risk tradeoff later. |
| What should mass revert promise? | **Automatic safe suffixes, preserved conflicts and partial results.** | A general interleaving-aware semantic inverse is substantially more complex and can still be wrong. Do not delay useful automation for it or silently overwrite human edits. |
| How long should rollback data live? | **90 days with visible deadlines, pinned live operations and an explicit storage budget.** | Gives a practical detection window while avoiding an unbounded state store. Indefinite history requires accepting ongoing storage growth. |
| Should purging a source redact managed derivatives whose recorded inputs include it? | **Yes; redact the whole artifact when field-level lineage is unavailable, while preserving the named retained classes.** | Otherwise copied secrets survive in current files after their snapshots/transcripts are redacted. This conservative rule can remove useful mixed-source content and must be visible in the purge preview. |
| Can admin API keys create broader credentials/grants? | **Remove that autonomous expansion path; use stepped-up interactive issuance/expansion.** | Necessary for the promise that humans author authority. This intentionally changes existing SEC-10/M0 behavior and needs migration documentation. |
| Should `before` remain supported? | **Yes as an explicit stricter mode, never as a way to bypass grants/hard gates.** | Useful for sensitive collections or incident recovery without burdening the default owner workflow. |
| What must ship with M2 rather than M3/M4? | **Snapshots, policy parity, bounded writes, citation states, freeze, safe revert and minimal owner UI/CLI.** | Those mechanisms justify the new default. Full visual polish, broad semantic merge, and automatic anomaly classifiers can wait. |
| Are the proposed quotas and 95% routine-write target appropriate? | **Adopt as initial values and tune from the owner's recorded workloads before closure.** | Public incident counts and competitor marketing cannot select these values for this installation. Keep protective limits explicit and adjustable. |
